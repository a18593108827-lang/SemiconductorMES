# EVAL-0001 追溯包抽屉并发下载：双按钮无重入闸，loading 错乱且旧请求清空新会话状态

> 来源：CP-6 真机验收（2026-09-22）用户实测发现并修复 · 归属：History（客诉追溯包前端 `ComplaintPackageDrawer`）· 治理规则 G5
> 性质：**验收期缺陷**（未上线、未推送即被拦下）；本文件是本项目启用 `docs/eval/` 后的第 1 条
> 修复提交：`0f642aa`

## 触发条件

- 追溯包已生成（抽屉 built 态），footer 有「下载 JSON」「下载 ZIP」**两个**按钮——CP-6 把 CP-4 的单按钮「下载证据」拆成两个
- 操作序列（任一即可）：
  1. 快速依次点两钮，或同一钮连点两次 → 两个下载请求并发在途
  2. 下载在途时关闭抽屉 → 换另一个 Lot 重开 → 新会话又被下载（旧请求此时才收尾）
- 数据特征无关：包越大（成员 × 履历）窗口越长，命中概率越高；小包也可能命中

## 复现步骤

1. `/app/history`（或 Lots 详情）搜到 Lot → 「生成追溯包」→ 抽屉进入 built 态
2. 快速依次点「下载 JSON」「下载 ZIP」
3. 观察：两个请求并发在途；**先完成者的 `finally` 把 `downloading` 置 null** → 后者的 loading 态消失、按钮重新可点，继续点会叠加更多并发
4. 变体：下载在途时关闭抽屉 → 用另一批次重开 → 旧请求的 `finally` 会清掉**新会话**的下载态（新会话按钮误变可点 / loading 提前消失）

## 预期正确行为

- 同一时刻**至多一个**下载在途；任一在途时两个按钮同时 disabled
- 旧会话（抽屉重开、`packageId` 变更）的请求收尾**不得**改写新会话的 UI 状态
- 失败提示只对应当前会话发起的请求

## 根因

`downloading` 只用 React state（三态 `'json' | 'zip' | null`）做互斥，缺两样东西：

1. **同步重入闸**：`setDownloading(format)` 是异步的，两次点击之间的同步窗口里 `downloading` 仍是 `null`，第二次点击照样发出请求
2. **会话归属**：`finally` 无条件 `setDownloading(null)`，不区分「这个收尾属于哪一次会话 / 哪一个请求」，于是旧请求清掉新状态

CP-4 只有单按钮、且失败即整块重来，暴露不出来；CP-6 拆双按钮 + 引入三态模型后放大成真实缺陷。

## 修法（已落地）

`web/src/components/lot/ComplaintPackageDrawer.tsx`

| 手段 | 作用 |
|------|------|
| `downloadingRef`（`useRef`） | 同步重入闸：`doDownload` 入口 `downloadingRef.current != null` 直接早退，不受 state 异步影响 |
| `downloadSeq`（`useRef<number>`） | 会话序号：抽屉重置（`open` / `anchorLotId` 变更）时 `+= 1`；`finally` 仅当 `downloadSeq.current === seq` 才清状态，旧会话收尾自动降级为 no-op |
| 两钮 `disabled={packageId == null || downloading != null}` | 视觉与行为一致：在途时两钮都锁 |

**自动化（2026-09-23 落地，首选）** —— 计划：`docs/架构/EVAL-0001-plan.md`

```bash
cd web && npm test        # vitest run：2 条行为用例（jsdom + Testing Library）
```

| 用例 | 覆盖的故障模式 |
|------|----------------|
| 同一批次内连点两个下载按钮只发出 1 个请求，且在途时两钮都禁用 | `downloadingRef` 同步重入闸——在 React 提交之前连点，此时 DOM 的 `disabled` 尚未更新，只有 ref 能挡住第二次请求 |
| 抽屉重开后，旧会话请求的收尾不得清掉新会话的下载态 | `downloadSeq` 会话归属——旧请求 `finally` 不得改写新会话状态 |

CI：`.github/workflows/ci.yml` 的 `web` job 已挂 `npm test`（失败即红）。

**两条断言都做过反向验证**（摘掉对应守卫 → 用例立刻变红，随后还原）：摘 `downloadingRef` 早退 → 用例 1 报 `expected to be called 1 times, but got 2 times`；摘 `downloadSeq` 比较 → 用例 2 报「找不到 `处理中…` 按钮」（新会话 loading 被旧请求清掉）。

**兜底校验**（自动化之外的补充）

- 手工：built 态快速连点两钮 → Network 面板**只有 1 条**下载请求；另一钮呈 disabled；结束后两钮恢复
- 手工：下载在途 → 关闭抽屉 → 换批次重开并下载 → 新会话 loading 正常，不被旧请求清掉
- 代码断言（可 grep）：`doDownload` 入口含 `downloadingRef.current != null` 早退；`finally` 被 `downloadSeq.current === seq` 包裹；两钮 `disabled` 含 `downloading != null`
- 构建：`npx tsc -b` 通过
