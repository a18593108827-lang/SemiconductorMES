# INT-0001 封测颗级追溯与测试数据回流（后道主线）

> 发起人：用户 / 记录：AI 会话 / 状态：draft
> 用法：意图只写问题与验收口径，**不写实现方案**；采纳后进入规格阶段（跨模块 → `docs/方案/`，模块内 → `docs/模块/{模块}/`）

## 1. 问题

**谁在痛**：封测厂的**质量工程师**（应对客户审厂与客诉）、**现场操作员**（不良处置）、**工艺工程师**（追异常来源）。

**现在什么痛**：

1. **追溯只到「批」**：现有 History 与客诉追溯包以 Lot 为单位，回答不了「**这一颗**来自哪片 wafer 的哪个位置、经过哪台设备哪段时间」。客户要求精准召回时，只能整批处理。
2. **测试结果在系统外**：CP/FT 分档（Bin）结果散在测试机单机、Excel、纸质记录里；系统内查不到「这批测了什么程序、分了几档、每档多少颗」。
3. **不良处置靠人**：不良 Bin 出来之后是否 Hold、要不要 Rework，靠人判断与线下沟通——既慢，又没留痕。

**代价（现状量级）**：客户审厂与客诉要求「15 分钟内给出任意批次的全流程证据链」（车规按 IATF 16949 / VDA 6.3 / AEC-Q 审）；现在这个动作要人工翻多个来源，以小时—天计。召回粒度错一代，报废与赔付按整批计。

## 2. 拟议成果（验收口径）

1. 任取一个封装成品（或一条 Strip），能把链路查出来并展示：所属封装批 → 来料 wafer lot → 关键工序 / 设备 / 时间，且**在分钟级内完成**（不出系统、不翻 Excel）。
2. 测试结果进系统并与批次绑定：任取一条测试记录，可查到所属批、测试程序版本、各 Bin 数量与占比。
3. 不良 Bin 可触发 Hold 或 Rework **建议**，人工确认后生效，并留下状态变更留痕（走既有事务日志）。
4. 客诉追溯包的导出物（JSON / ZIP 证据包）里能带上上述**颗级与测试分档信息**。
5. **现场不退化**：完成一次 TrackIn/Out 的步数与现状相同（现场 3 步内过站）。

## 3. 受影响用户与系统

- 用户 / 角色：质量工程师（审厂 / 客诉 / 8D）、现场操作员（不良处置）、工艺工程师（异常追溯）
- 模块：Lot / Track / Hold / History（客诉追溯包）/ 报表；可能新增封测特化能力位
- 表 / Facade：待规格阶段确定；跨模块访问一律走 Facade

## 4. 约束

| # | 约束 | 说明 |
|---|------|------|
| A1 | 状态唯一真相仍在 Track | 测试数据与自动建议都不得直接改写 Lot 状态；Hold / Rework 必须走既有事务 |
| A2 | 测试数据接入先用文件 / API | SECS/GEM 属远期；本期不得因设备协议阻塞主线 |
| A3 | 追溯链不得依赖人工补录 | 若某段链路只能手工填，本期视为未达成 |
| A4 | 导出沿用既有口径 | 不落盘、不缓存；权限沿用原权限码（如 `complaint:view`） |
| A5 | 不破坏现场 3 步过站 | 新增字段或步骤不得加长过站路径 |
