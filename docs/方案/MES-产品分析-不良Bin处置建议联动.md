# MES 产品分析 — 不良 Bin 处置建议联动（TD-2）

> 分析：AI 会话 / 状态：draft（站在产品视角回答「TD-2 做的是什么、为谁做、值不值、做到哪算够」）
> 输入：`MES-业界调研-不良Bin处置与HoldRework联动.md`（J1–J11）· 方案 §6 边界
> 一句话定位：**TD-2 是把 TD-1 沉淀的 Bin 数据资产，变成一道"主动找上门"的质量防线** —— 数据不再等人来查，超限自动举牌，人来拍板。

---

## 1. 产品问题定义

### 1.1 现状空窗（TD-1 之后）

TD-1 上线后，系统**有了**：测试记录、Bin 汇总、Strip、客户映射、客诉证据链。但数据是**被动的**——

| 空窗 | 描述 | 代价 |
|------|------|------|
| 没人主动看 | Bin 数据落库后无任何预警，超限批要靠工程师**想起来去翻** | 发现滞后：人工排查典型小时~天级（yieldHUB：Subcon hold 批滞留数天） |
| 判据没固化 | 「bin 3 占比超过多少算异常」在老师傅脑子里，人走了判据也走 | 经验不可复制，新人厂判断不一致 |
| 质量兜底缺最后一环 | 不良批继续流转/出货的风险**完全依赖人工纪律** | 封测厂最大质量事故 = 不良批流出客户 |
| 审核答不上 | 车规客户稽核（IATF 16949 / AEC-Q008 意识）必问「超限批怎么管理」 | 现在答案是空白，影响客户信任与订单资格 |

### 1.2 产品命题

> **把「判据」从人脑搬进系统，把「发现」从人找事变成事找人，把「处置」留在人手里。**

机器做三件事：算（占比对比阈值）、举牌（生成建议单）、记（全程留痕）。
人只做一件事：拍板（确认 → 走既有 Hold/Rework 事务；忽略 → 记原因）。

---

## 2. 用户与场景

| 角色 | 在 TD-2 里做什么 | 核心诉求 | 频次预估 |
|------|------------------|----------|----------|
| 测试工程师 | 提交测试记录（触发方，无感）；处理自己触发的建议 | 提交后立刻知道「这批有没有问题」，不要事后被追责 | 每日多批 |
| 质量/品质工程师 | **主要用户**：配置阈值规则、确认/忽略建议单、给出处置 | 不漏批（防流出是 KPI）；误报别太多；留痕能应付稽核 | 每日 |
| 生产/计划 | 被动方：批被建议 Hold 影响交付 | 处置要快、理由要透明、能查进度 | 被动 |
| 产品/工艺工程师 | 看建议趋势，反推工艺/程序问题 | 建议单里有足够上下文，少跑系统 | 每周 |
| 管理层/客户稽核 | 只看结果 | 「超限批 100% 有记录、有处置、有责任人」 | 月/季 |

**典型场景（确认路径）**：测试工程师提交 FT 记录 → 系统 1 秒内判定 bin 3 占比 4.2% > 阈值 2% → 生成建议单（含批、bin、占比、规则快照）→ 质量工程师在管理端 Test 页看到举牌 → 查看建议上下文与该批履历 → 一键「确认 → 建议 Hold」，系统预填原因码走既有 Hold 事务，建议单回写 tx_id → 批停住，等人调查。

**典型场景（忽略路径）**：质量工程师判断为测试程序误判 → 点「忽略」→ **必填原因枚举**（如误判/历史已放行/重复建议）→ 留痕。忽略率成为规则质量的健康指标。

## 3. 价值主张与优先级论证

| # | 价值 | 说明 | 强度 |
|---|------|------|------|
| V1 | **防流出（质量兜底）** | 不良批在流转/出货前被系统举牌；这是封测厂质量事故的最后一道闸门，也是 INT-0001「客诉证据链」的事前半段 | 核心卖点 |
| V2 | **压缩发现-处置时延** | 从「数天滞留」（业界 Subcon 现状）压到「分钟级举牌 + 当日处置」 | 可量化 |
| V3 | **判据资产化** | 阈值规则显式配置，老师傅经验可传承、可审计、可调优 | 长期复利 |
| V4 | **稽核合规** | 「每个超限批都有建议、有决定、有留痕」直接回应车规客户零缺陷审核 | 车规路线必需 |
| V5 | **激活 TD-1 投资** | TD-1 的数据从"存了"变"用了"，是 INT-0001 主线闭环（验收 3）的关键一步 | 主线承诺 |

**为什么不建议跳过 TD-2 先做别的**：验收 3 是 INT-0001 三条验收里唯一还没着落的；且 V1 是车规厂型的资格性问题，不是锦上添花。同时它比 TD-3（颗级/STDF）便宜得多——复用 TD-1 全部数据模型，只加一层判定+一张建议单。

## 4. MVP 边界（P0 / P1 / 后置）

### P0 —— 建议单最小闭环（TD-2 本体）

1. 阈值规则配置：产品 / 程序版本（可空回退，对齐 D14）/ bin / 占比上限，静态值手工配（J1：SBL 后置）
2. 判定时机：测试记录落库成功后同步判定（J11：手工/API 提交天然近实时）；**每个超限 bin 一条建议明细**（J3）
3. 建议单 `mes_test_advice`：**快照触发时的 bin 数与规则**（J4，防字典改动污染证据链）
4. 处置动作：确认 → 建议 Hold / 建议 Rework（复用既有事务，回写 tx_id）；**忽略必填原因枚举**（J6）
5. 建议类型仅三种：**建议 Hold / 建议 Rework / 建议重测**；scrap 不进（J5）
6. 管理端 Test 页加「处置建议」Tab（列表 + 详情 + 操作）；现场台零改动（A5）
7. 权限：`test:advice-view` / `test:advice-confirm`（两级命名先例 `track:track-in`）

### P1 —— 运营完善（可同刀或紧随）

- 超期升级：待确认超 N 天自动提醒（不默认报废，J7）
- Alarm 复用：确认时可选 raise 一条告警（方案 §6 第 4 条）
- 忽略原因统计视图（规则调优入口）

### 后置（明确不做，写进功能清单防 scope creep）

- SBL/SYL 统计限自动计算与滚动更新（数据不足，J1）
- 返工次数限额 Rework Limits（J8）· Lot Commonality 兄弟批共案（J10）
- 重测重定向指定 test 程序（涉及 Dispatch/Recipe 联动）· 自动处置/自动报废（P7 红线）· 颗级 outlier（TD-3/YMS）

## 5. 成功指标（上线后可判真假）

| 指标 | 定义 | 目标 |
|------|------|------|
| 举牌时延 | 测试记录落库 → 建议单生成 | < 1 分钟（同步判定，天然达成） |
| 拦截完整率 | 超限批中产生建议单的比例 | 100%（规则命中即举牌，系统保证） |
| 处置时延 | 建议单生成 → 确认/忽略 | 中位数 < 1 天（对标 MRB「< 7 天」收紧一个量级） |
| 悬单率 | 待确认超 3 天的建议单占比 | < 10%，且逐周下降 |
| 忽略率 | 忽略 / 总建议 | 供监控不设目标：过高说明阈值误报多，过低反而要警惕"全确认"走过场 |
| 稽核问答 | 车规客户/稽核问「超限批怎么管」 | 能直接调出建议单列表作答 |

## 6. 风险与待拍板

| # | 风险/问题 | 产品对策 | 待拍板 |
|---|-----------|----------|--------|
| R1 | **冷启动**：初始阈值没人给得准 | 首版阈值允许全空（不配规则=不举牌，系统不添乱）；给一份按 bin 类型的默认模板（如 functional bin 2%、边缘 bin 5%）供导入；运营 4–8 周后再谈收紧 | 模板是否本期做 |
| R2 | **建议疲劳（狼来了）**：误报多 → 用户习惯性忽略 → 防线失效 | 忽略必填原因 + 忽略率看板 + 超期升级；规则粒度细到「产品+程序版本」减少一刀切误伤 | — |
| R3 | **确认权责**：谁能忽略？生产想快放、质量想保守，利益冲突 | 参照 MRB 精神：**确认/忽略权只给质量侧角色**，生产侧只读；忽略权限单列（比确认更敏感） | 角色映射 |
| R4 | **触发依赖录入纪律**：手工提交时代，不录数=不判定 | TD-2 不解决（录入纪律属 TD-1 运营）；在建议单页明示「仅覆盖已提交记录」，管理预期 | — |
| R5 | 与 Hold 模块的体验衔接 | 确认动作内嵌在建议单里完成（不必跳 Hold 页），Hold 表单预填批号+原因码 | — |
| R6 | 权限编码与菜单树影响 | 新增 perm_code 走既有种子流程；`sys_permission` 当前 MAX(id) 需实测续接 | plan 阶段核 |

## 7. 竞品视角一句话

大厂路径是「MES 内建异常流（CM）+ YMS 外挂分析（yieldHUB/yieldWerx）」两条腿，YMS 一套就是重资产投入。本项目选择 **MES 内建轻量建议单**：不做分析平台，只做「判定-举牌-处置-留痕」闭环——这正是 MVP 收敛哲学（深度按 MVP 收敛，不按满配一次做完）的延续，将来若要 SBL/共案分析，advice 落库的数据天然是分析底座。
