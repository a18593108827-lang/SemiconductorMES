# MES 文档体系重构方案（AI 原生 SDLC 对齐）

> 版本：v1.1
> 对齐：Anthropic《AI 原生 SDLC 实战手册》（2026-08-21）· `docs/架构/半导MES架构设计.md` 现行体例
> 更新：2026-09-20
> 状态：**已批准（2026-09-20）** —— Doc-1 / Doc-2 已实施；Doc-3 待试运行
> 原则：**不推翻、不重命名** —— 现有 91 篇文档是资产，只补「构建之后」缺失的环节；模板固化新流程

---

## 0. 为什么重构

### 0.1 现状对标（已核实仓库）

| 阶段 | 手册要求 | 本项目现状 | 结论 |
|------|----------|------------|------|
| 规划 | intent.md 意图规格 | `docs/业务清单/` + `docs/方案/`，切片体例（Car-6→7→8） | 已具备，缺统一入口与编号 |
| 设计 | spec.md 设计规格 | `docs/模块/{模块}/` 五件套 | 已具备 |
| 构建 | plan.md + 根级上下文 | 会话记忆存在（`.workbuddy/memory/`），不在版本控制内 | **部分具备，缺 AGENTS.md 与切片 plan** |
| 测试 | 反馈回路 + eval | `server` 无 `src/test`、无 CI | **缺口（本方案只建文档位，工程另行立项）** |
| 部署 | 审查策略 + 门禁 | 无 CI/CD | 缺口（后置，不在本方案范围） |
| 维护 | 监控 + 事故回流 | `MES-实施进度与下一步.md` 承担回流；Agent 数据暴露已立项 | 部分具备 |

### 0.2 重构要解决的四个问题

1. **意图没有独立产物**：需求入口分散在业务清单/方案/口头，无编号、无状态、不可追溯
2. **切片缺「计划先行」环节**：切片表写了交付什么，但无获批的 plan 作为实现基准与审计对象
3. **机构知识不在版本控制内**：架构铁律在会话记忆里，换人/换工具即丢失，也无法随代码审查
4. **文档头部人读机不读**：blockquote 头部优秀但非结构化，AI 无法批量索引、无法按状态过滤产物链

## 1. 目标形态：一条产物链

```
docs/intent/INT-{N}-*.md          意图（发起 → 采纳/拒绝）
        │ 采纳后
        ▼
docs/方案/ + docs/模块/五件套        规格（现有体系不动）
        │ 切片立项
        ▼
docs/模块/{模块}/{切片号}-plan.md    计划（获批后才能动码）
        │ 实现完成
        ▼
代码 + 「已完成功能」文档更新         证据（现有体系不动）
        │ 生产事故 / 缺陷
        ▼
docs/eval/EVAL-{N}-*.md            回归用例（后置启用）
        │ 生成新意图
        ▼
回到 INT                            循环自我供给
```

**根级 `AGENTS.md`** 贯穿所有环节：每次 AI 会话的第一上下文。

核心设计三条（来自手册，逐条落地）：

| # | 设计 | 落地物 |
|---|------|--------|
| D1 | 产物即审计轨迹 —— 意图采纳、计划获批都是 git 提交，不靠口头 | INT 状态流转 + plan 状态流转 |
| D2 | 人类可读且机器可执行 —— 头部 frontmatter 结构化 | §3 统一头部规范 |
| D3 | 模板固化流程 —— 新需求/新切片必须从模板起稿 | `docs/_templates/` 四件 |

### 1.1 与手册概念对照

| 手册概念 | 本项目对应物 | 动作 |
|----------|--------------|------|
| intent.md | `docs/intent/INT-{N}-*.md` | 新增 |
| spec.md | `docs/方案/` + 模块五件套 | 保留不动 |

| CLAUDE.md | 根级 `AGENTS.md` | 新增 |

## 2. 目录结构（增量调整）

现有目录**全部保留、不改名**（见 D4）。仅新增四处：

```
MES/
├── AGENTS.md                      # 新增：根级上下文，AI 会话第一入口
└── docs/
    ├── intent/                    # 新增：意图规格（INT-0001-*.md）
    ├── _templates/                # 新增：四件模板
    │   ├── INT-模板.md
    │   ├── plan-模板.md
    │   ├── EVAL-模板.md
    │   └── AGENTS-骨架.md
    ├── eval/                      # 新增：事故回归用例（后置启用，先建目录占位）
    ├── 方案/                      # 保留
    ├── 架构/                      # 保留（本文档所在）
    ├── 业务清单/                   # 保留
    ├── 模块/{模块名}/              # 保留五件套；切片 plan.md 也放这里
    └── UI/                        # 保留
```

**产物放哪**：切片 plan 与所属模块同目录（如 `docs/模块/Carrier（载具）模块/Car-9-plan.md`），不另设 plan 目录——保证 plan 与功能清单、已完成功能同处一地，互相链接零成本。

## 3. 统一头部规范（frontmatter）

所有**新增**文档使用 YAML frontmatter；**存量**文档在 Doc-2 批量补齐（只加头、不动正文，见 D5）。

```yaml
---
type: intent          # intent | 方案 | 架构 | 功能文档 | 数据库设计 | 接口设计
                      # | 功能清单 | 已完成功能 | plan | eval | 进度
                      # | 业务清单 | UI | WI | INDEX   ← v1.1 扩充：覆盖存量类型
module: Carrier       # 模块名；跨模块留空
status: draft         # 见下方状态语义表
slices: []            # 关联切片号，如 [Car-9]
aligns: []            # 上游产物文件名，如 [MES-Carrier架构设计.md]
updated: 2026-09-20
---
```

frontmatter 之下，**保留现有 blockquote 头部体例不变**（对齐/前提/口径/更新/状态），两者互补：frontmatter 给机器，blockquote 给人。

### 3.1 状态语义

| type | 合法状态 | 流转含义 |
|------|----------|----------|
| intent | draft → accepted / rejected | accepted = 进入规格阶段；rejected = 关闭留档（写拒绝理由） |
| plan | draft → approved → done | approved = 允许动码（审批提交即审计）；done = 实现与验收完成 |
| 功能清单 | draft → in-progress → done | 现行约定不变 |
| 已完成功能 | done | 只增不改 |
| eval | active | 事故沉淀即生效 |
| 方案/架构/其余 | draft → done | 现行约定不变 |

## 4. 模板（四件）

### 4.1 INT 模板（意图规格）

```markdown
---
type: intent
module: 
status: draft
slices: []
aligns: []
updated: 
---
# INT-{N} {一句话名称}

> 发起人： / 记录：AI 会话 / 状态：draft

## 1. 问题
现在什么痛、谁在痛、代价多大（尽量量化）。只描述现状，不描述方案。

## 2. 拟议成果
验收口径：做完后能观察到什么（可判真假的陈述）。**不写实现方案。**

## 3. 受影响用户与系统
- 用户/角色：
- 模块：
- 表 / Facade：

## 4. 约束
| # | 约束 | 说明 |
|---|------|------|
| A1 |  |  |

## 5. 未决问题
- [ ] 
```

要点：正文中文、口语化、发起人自己的语言；AI 可代笔但发起人**必须在采纳前逐条核对**。

### 4.2 plan 模板（切片计划）

```markdown
---
type: plan
module: 
status: draft          # draft → approved → done
slices: [{切片号}]
aligns: [上游 INT 或 功能清单文件名]
updated: 
---
# {切片号} 计划 — {名称}

> 对齐：{上游产物 §节} · 状态：draft（未批不动码）

## 1. 目标与边界
一句话目标。做什么 / **不做什么**（负面清单必须写）。

## 2. 接口清单
| 方法 | 路径 | 权限码 | 说明 |
|------|------|--------|------|

## 3. 表变更
新表 / 改表 / 种子数据（含表前缀，按模块分）。

## 4. 影响的 Facade 与模块
跨模块只走 Facade；列出将被调用/修改的 Facade 方法。

## 5. 实现步骤
子步骤 a/b/c，含顺序依赖与禁止乱序项。

## 6. 测试与验收
- 验收标准（可判真假）：
- 验证方式（命令 / 页面 / SQL）：

## 7. 回滚方式
配置开关 / 数据回退 / 不需要，三选一并说明。
```

要点：**一份 plan 必须让没参与讨论的人能独立实现**；实现偏离时先改 plan 再改码。

### 4.4 AGENTS.md 骨架（根级上下文，一页以内）

```markdown
# AGENTS.md — MES 项目上下文

## 项目定位
半导体 MES（对标 SiView / Camstar 的 Lot Tracking 模型）。
Track 事务为唯一执行真相；状态不可被多模块改写。

## 模块铁律（违反即返工）
| # | 铁律 |
|---|------|
| 1 | 状态唯一真相在 Track；禁止 WIP/Track 双写 |
| 2 | 禁止 PUT 冒充分批改 qty |
| 3 | Recipe / Reticle 不进 Route body（运行时解析） |
| 4 | 跨模块只走 Facade（Carrier/Recipe/Edc/History/Report） |
| 5 | 状态变更必写 mes_tx_log；表前缀按模块分 |
| 6 | Route 只认 Lot.route_version_id 快照，禁读直播表跳站 |

## 技术栈与运行
Java 21 + Spring Boot 单体模块化 + MyBatis-Plus + MySQL + Redis + Sa-Token。
包结构 com.mes.{module}，每模块 api/application/domain/infrastructure。

## 文档体系（会话必读入口）
- 新需求从 docs/_templates/INT-模板.md 起稿 → docs/intent/
- 切片动码前必须有 {切片号}-plan.md 且 status: approved
- 模块文档：docs/模块/{模块}/（功能文档/数据库设计/接口设计/功能清单/已完成功能）
- 完成后必须更新「已完成功能」+ docs/架构/MES-实施进度与下一步.md

## 常见错误（AI 犯两次即写入本节）
- （随项目演进追加）
```

## 5. 约束、禁止与决策

### 5.1 约束表

| # | 约束 | 说明 |
|---|------|------|
| A1 | 产物即审计 | 意图采纳、计划获批均以 git 提交为准，禁止口头放行 |
| A2 | plan 未批不动码 | 切片代码提交必须先有 status: approved 的 plan |
| A3 | 完成即同步 | 切片落地后同会话更新「已完成功能」与实施进度文档 |
| A4 | frontmatter 最小集 | 六字段（type/module/status/slices/aligns/updated），不多加 |
| A5 | 双头并存 | frontmatter 供机器索引；blockquote 头部供人阅读，互不替代 |
| A6 | AGENTS.md 一页 | 超一页即拆分到模块文档；AI 犯同一个错两次才写入 |

### 5.2 禁止表

| # | 禁止 | 理由 |
|---|------|------|
| P1 | 重命名/移动存量文档与目录 | 91 篇文档间的相对链接会全部断裂 |
| P2 | Doc-2 批量补头时改正文内容 | 只加 frontmatter，正文一字不动，diff 可审 |
| P3 | INT 里写实现方案 | 意图只描述问题与验收口径，方案属规格阶段 |
| P4 | 回填历史切片的 plan/intent | 已落地内容以「已完成功能」为真相，不造历史 |
| P5 | 把 `.workbuddy/memory` 当唯一知识载体 | 会话记忆不进版本控制；铁律必须落 AGENTS.md |

### 5.3 决策表

| # | 决策 | 理由 |
|---|------|------|
| D1 | 意图独立成目录而非并入业务清单 | 业务清单是全景态，INT 是单个需求的时序态；两者粒度不同 |
| D2 | plan 放模块目录而非独立目录 | 与功能清单/已完成功能同地，链接与审查零成本 |
| D3 | 中文目录/文件名保留 | 与存量一致；frontmatter 的 type 字段已承担机器分类 |
| D4 | INT 编号四位（INT-0001） | 排序友好；预留千级余量 |
| D5 | eval 目录先建后用 | src/test 与 CI 未建，但文档位先占，避免事故发生时无处可写 |

## 6. 治理规则（G#）

| # | 规则 | 检查时机 |
|---|------|----------|
| G1 | 新需求必须从 INT 模板起稿，否则不进入规格阶段 | 方案/功能清单立项时核对 aligns 链 |
| G2 | 切片 plan 的 status 必须走到 approved 才允许提交代码 | 代码评审时核对 plan 状态 |

| G4 | 模板变更走文档评审 | `_templates/` 目录的任何提交 |
| G5 | 每起生产事故/线上缺陷产出一条 EVAL | 事故复盘时 |
