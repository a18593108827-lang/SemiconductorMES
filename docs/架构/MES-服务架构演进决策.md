# MES 服务架构演进决策 — 单体、Spring Cloud 与外围系统

> 版本：v0.4（v0.3 基础上补前端形态演进章节）

> 定位：回答五个问题——① 现有单体 Spring Boot 要不要升级 Spring Cloud；② Agent 服务要不要独立微服务；③ 后续接入 ERP / APS 算不算「上微服务体系」；④ OA 接入与 SSO 统一身份怎么处理；⑤ 前端现在只有一个，后续长什么样
> 更新：2026-09-18

## 0. 结论（一句话）

**后端：不升级 Spring Cloud；维持模块化单体；Agent / APS 独立服务；ERP / OA 是外部集成边界（防腐层 + 最终一致）；SSO 是横切身份基础设施（提前拍板，认证归 IdP、授权留本地）；治理组件按需单件引入。前端：从一个应用演进为「单仓库多应用」（apps/admin · field · dashboard + packages 共享层），先构建分离、不急仓库分离；不上微前端；APS 甘特由 APS 服务自带；现场台写操作永远在线。**「升级到 XX 体系」的心智模型在后端和前端都不成立——正确的模型都是：**边界随业务自然生长，结构滞后半拍跟进。**

## 1. 决策表

| # | 决策 | 选择 | 核心理由 |
|---|------|------|----------|
| D1 | MES 核心 | **模块化单体**（维持现状，强化模块纪律） | 事务强一致是铁律；团队规模未到；微服务四收益中三项不存在 |
| D2 | Spring Cloud | **不上全家桶**（组件按需单件引入） | 治理组件在服务数 <3 时是纯负担；单人/小团队运维成本不可承受 |
| D3 | Agent 服务 | **独立进程 + 独立仓库**，第一天就拆 | 故障域隔离（LLM 慢/挂不能影响 Track）+ 技术栈异构 + 安全边界 |
| D4 | 集成契约 | Agent→MES 走 REST（Tool Facade）；MES→Agent 走 RocketMQ；**禁止共享 DB 与共享 Jar** | 与 Agent 数据暴露规划 D1/P1 一致 |
| D5 | Agent 技术栈 | **Java + Spring AI / LangChain4j**（推荐）；Python 仅在 ML 训练管线引入 | 单团队同栈，运维/鉴权/日志复用；训练与推理分离 |
| D6 | 后续拆分 | Adapter、数采**必然**独立（触发即拆）；只读报表**条件**独立；Track 事务核**永不**拆 | 见 §4 触发条件表与拆分禁区 |
| D7 | ERP 接入 | **外部集成边界**，做防腐层（ACL）：先单体内 `erp-adapter` 模块，异构/高频后独立 | ERP 是买来/既有系统，永远不是你的微服务；难点在一致性不在服务化 |
| D8 | APS 接入 | **独立计划服务**（独立部署、另库、REST/MQ），对齐 APS 方案稿既有决策 | 资源画像/可用性/迭代节奏/数据自治四条理由，与 Agent 同构 |
| D9 | OA 接入 | **外部协作系统集成**，同 D7 模式：`oa-adapter` 防腐层；审批/通知/人员同步/待办四场景 | OA 是审批与协作的壳，**业务真相仍在 MES**；外部系统 ≥3 家后合并 integration 服务 |
| D10 | SSO 统一身份 | **横切基础设施，不是微服务**：优先接集团 IdP；无则 Sa-Token SSO Server 过渡（MES 兼任），长期独立 IdP；**先于 Agent/APS 落地前拍板** | 身份边界影响所有服务的认证链路，后改成本 ×N；禁止把统一身份永久焊死在业务 MES 上 |
| D11 | 前端仓库形态 | **单仓库多应用**（monorepo）：`apps/admin · field · dashboard` + `packages/ui · api-client · types`；**先构建分离（Vite 多入口），不急仓库分离** | 一个仓库的纪律 + 多入口的隔离；单人团队多仓库成本高 |
| D12 | 微前端 | **不上**（qiankun / Module Federation） | 微前端解决多团队独立发布前端的组织问题；单团队上微前端 = 纯负担 |
| D13 | 新面前端归属 | AI Copilot = MES 前端组件（调 Agent SSE）；知识管理后台 = Admin；**APS 甘特 = APS 服务自带**；移动端不做原生 App（OA 待办 + 深链回 Web，必要时 PWA） | 谁的领域谁的 UI：AI 交互属 MES 面，甘特编辑器与计划库同源迭代 |
| D14 | 现场台在线纪律 | 只读数据可缓存；**写操作（过站/Hold/扫码）必须在线** | 离线缓冲过站 = 状态真相失控；现场 3 步 Track 是产品成功标准 |

## 2. 论证一：为什么不上 Spring Cloud

### 2.1 微服务解决什么 vs 我们有什么

微服务的四个真实收益，逐一对照本项目现实：

| 微服务收益 | 成立条件 | 本项目现状 | 结论 |
|------------|----------|------------|------|
| 组织扩展（康威定律） | 多团队并行开发争用代码库 | 单人/极小团队 | ❌ 不存在此问题 |
| 独立部署 | 模块发布频率差异大、互相阻塞 | 统一发布窗口即可接受 | ❌ 收益≈0 |
| 故障隔离 | 单模块故障拖垮整进程 | Track 强事务低流量，风险在代码不在进程边界 | ❌ 收益≈0 |
| 技术异构 | 需要不同运行时（LLM/Python/GPU） | **真实需求 = Agent / APS 等外围能力** | ✅ 用独立服务即可满足，不需要治理全家桶 |

### 2.2 最硬的论据：事务一致性

Track 事务的既有模型（架构总册 §5.4）：

```
分布式锁(lotId) → 加载 Lot+RouteStep+Hold+Eqp → 校验
  → 单 DB 事务更新 Lot/WIP 投影 → 写 mes_tx_log → 提交后发事件
```

这是**单库事务内完成的强一致闭环**，是「状态唯一真相」的物理基础。若把 Track / Lot / Hold / WIP 拆成服务：

- 每次过站变成分布式事务 → Saga / TCC / Seata → 复杂度 ×5，且补偿语义与「不可逆事务需确认」的业务规则冲突
- Hold 校验跨网络调用 → 过站 P99 < 500ms 的目标被序列化延迟吃掉
- **直接破坏本项目最高架构铁律**（状态唯一真相、禁止双写）

结论：事务核拆分不是「成本高」，是「方向错误」。

### 2.3 Spring Cloud 的隐性成本清单

注册中心（Nacos）、配置中心、网关、链路追踪（SkyWalking）、熔断、分布式事务、每服务一条部署管道、本地联调环境 ×N、日志聚合……每一项对单人团队都是**持续税负**，且没有任何一项解决当前的真实痛点。

### 2.4 业界佐证

- 本项目架构总册 §12 风险 5 早已预言：「一上来 Spring Cloud → 不必要，先单体」——本文是对该风险的正式闭环
- 大厂商用 MES 亦非微服务神话：SiView / Camstar 核心是中央服务 + 外围适配进程的形态；应用材料 SmartFactory 的 AI 能力是**同源集成的外围模块**，而非把 CIM 拆成微服务群

## 3. 论证二：Agent 服务为什么要独立（但不是"微服务"）

### 3.1 独立的四个理由

| # | 理由 | 说明 |
|---|------|------|
| R1 | **故障域** | LLM 调用秒级延迟、超时、限流是常态；Agent 挂/慢**不允许**影响 Track；单体发版不允许中断进行中的 AI 会话 |
| R2 | **技术栈** | LLM SDK / 向量库 / RAG 框架迭代快、依赖重（GPU、SSE 流式、长连接），不污染主工程依赖树 |
| R3 | **安全边界** | prompt 注入面、脱敏网关、出网策略需要独立审计与加固；与核心事务代码隔离 |
| R4 | **迭代速度** | AI 功能试错频率远高于业务模块，独立仓库独立发布，不占用 MES 发版窗口 |

### 3.2 但「独立」≠「上微服务体系」

两个服务（MES + Agent）之间：**DNS / Nginx 反代即可完成寻址，无需注册中心；配置各管各的，无需配置中心。** 服务数 <3 时，治理组件是负资产。Agent 数据暴露规划中 D3「MCP 仅作可选协议壳」同理——协议可以标准，治理不必提前上。

### 3.3 技术选型（D5 展开）

| 方案 | 优点 | 缺点 | 判断 |
|------|------|------|------|
| **Java + Spring AI / LangChain4j** | 与主栈同语言；复用 Sa-Token 生态、运维脚本、日志体系；单人维护成本最低 | LLM 生态比 Python 晚半年 | ✅ **推荐起步** |
| Python + FastAPI | RAG/ML 生态最全 | 第二语言第二套运维；单人团队心智负担 | ML **训练**管线用（L2 良率模型），推理结果仍可由 Java 侧服务化 |
| 混沌：塞进 MES 单体 | 零部署成本 | 违反 R1~R4 全部 | ❌ 禁止 |

### 3.4 集成契约（与既有规划对齐）

```
Agent ──REST──► MES Tool Facade（任务级，只读为主；service token + 用户权限透传）
MES  ──RocketMQ──► Agent（mes.lot.changed / hold.changed / alarm.raised 复用既有 Topic）
两者各自持有：自己的 DB schema / 自己的配置 / 自己的发布节奏
```

- 鉴权：Agent 持服务凭证调 MES；Tool Facade 侧做工具级权限映射（复用 Sa-Token 权限码）
- 审计：限流、审计钩子落在 Tool Facade（规划稿 §3 已定）
- LLM 网关：脱敏出站；模型可替换，接口层不绑死厂商

## 5. 外围系统接入（ERP / APS / OA）与 SSO：边界增长 ≠ 换体系

**先纠正问题本身**：「加入 ERP / OA 是不是就可以用微服务体系」——这个问法隐含了「体系切换」思维。正确的心智模型是：

1. **ERP 和 OA 都不是你要建的服务**。它们是买来的/既有的外部系统，永远以**外部集成边界**存在。你要建的是「集成适配（防腐层）」，不是收编。
2. **APS 是独立服务的正确候选**，但这是「再加一个像 Agent 那样的独立进程」，不是「切换体系」。
3. **SSO 既不是微服务也不是业务模块**，它是横切的**身份基础设施**，影响所有服务的认证链路。
4. 上述全部到位后运行单元来到 4~6 个，**这才第一次到了「值得引入部分治理」的门槛**——而且仍然从 Gateway 单件开始，不是全家桶。

### 5.1 ERP：集成边界 + 防腐层（D7 展开）

| 项 | 处理 |
|----|------|
| 形态 | 初期：单体内 `erp-adapter` 模块（包 `com.mes.erp`，表前缀 `mes_erp_*`，本地消息表）；多家异构/高频后独立 integration 服务 |
| 数据流 | ERP 工单/交期下发 → MES Lot 创建/放行；MES 完工/报废/工时报文 → ERP（双向） |
| 一致性 | **最终一致**：事务性发件箱（本地消息表 + MQ）+ 幂等消费 + 定时对账；**禁止跨系统强事务** |
| 防腐 | ERP 模型（工单 / BOM / 物料编码）只存在于 adapter 层，翻译成 MES 领域语言（Lot / Route）后才进核心 |

三条关键认知：

1. ERP 集成的难点从来不是「要不要微服务」，而是**对账、补偿、幂等**——这些在单体内做和独立服务做难度完全一样。
2. ERP 与 MES 之间**没有也不该有分布式事务**：两个自有库的系统间，业界唯一正解是事件驱动 + 幂等 + 对账（这与单体内部 Track 强事务是两个世界，别混淆）。
3. 防腐层的价值：ERP 换版本/换厂商时，MES 领域模型零改动——这是单体模块化红利的又一次兑现。

### 5.2 APS：独立计划服务（D8 展开，对齐 APS 方案稿）

APS 方案稿已定四件事：**独立系统、`aps-service` 独立部署、计划库另库、与 MES 同 JVM 长期混部不推荐**。本文从架构师角度补四条同构理由（与 Agent 服务完全同构）：

| # | 理由 | 说明 |
|---|------|------|
| R1' | 资源画像 | 排程求解计算密集（约束求解/启发式，分钟级重算吃 CPU），与 OLTP JVM 的低延迟调优目标冲突 |
| R2' | 可用性 | APS 挂了现场照常 TrackOut——计划是「指导」不是「闸门」（方案稿 §4：Track 不调用 APS，只消费已发布计划） |
| R3' | 迭代节奏 | 排程算法/约束规则试错频率高，不应占用 MES 发版窗口 |
| R4' | 数据自治 | 计划库（方案/版本/甘特/负荷）与 `mes_lot` 解耦，What-if 沙箱不污染执行数据；只经发布 API 交换 |

边界纪律沿用方案稿：MES→APS 只读导出（WIP/Eqp/工时快照）；APS→MES 只发已发布计划（`planId`/时间窗/建议机台组/优先级）；Dispatch 把 APS 建议当**软约束**。**甘特/负荷编辑器前端由 APS 服务自带**（见 §6.3）。

### 5.3 OA：外部协作系统集成（D9 展开，同 ERP 模式）

OA（泛微/致远/钉钉/企微/飞书任一形态）与 ERP 同类——**外部系统，防腐层集成，不是微服务**。四个典型集成场景：

| 场景 | 数据流 | 要点 |
|------|--------|------|
| **审批流** | MES 权限申请 / Hold 解锁 / Scrap 等敏感审批 → 推 OA 审批 → 回调 MES 生效 | 回调**验签 + 幂等**；**审批结果以 MES 本地落库为准**（OA 只是流程壳，业务真相在 MES） |
| **消息通知** | Alarm / 建议 Hold → OA 或企微/钉钉机器人 | 复用 Alarm 既有 HTTP 出口，加渠道适配即可 |
| **组织人员同步** | OA/HR 是人员主数据源头 → 单向同步 MES 用户表 | 方向固定：OA→MES，**禁止反向写**；离职/调岗按增量同步 |
| **统一待办** | MES 待办聚合到 OA 待办中心 | 只读推送，点击跳回 MES 深链 |

形态与演进：`oa-adapter` 模块（`com.mes.oa`，表前缀 `mes_oa_*`），与 `erp-adapter` 完全同构；当外部系统 ≥3 家（ERP + OA + 企微）时，把 adapter 们**合并**独立成一个 integration 服务（一套出站网关、一套验签/幂等/对账基建），而不是每家一个服务。

### 5.4 SSO：横切身份基础设施（D10 展开）

**定性**：SSO 不是微服务问题，也不是业务模块问题——它是**身份边界**问题，横切所有服务（MES、Agent、APS、将来的看板独立域）。

**第一决策：谁当 IdP（身份提供方）**

| 情形 | 方案 | 说明 |
|------|------|------|
| 集团已有统一身份（IAM / AD / 企业微信身份） | MES 做 **Client 接入**（Sa-Token SSO Client / OIDC / CAS） | 保留本地超管**破窗账号**（IdP 故障时兜底） |
| 集团没有，短期也不建 | **过渡：Sa-Token SSO Server，MES 兼任 IdP** | 现有用户体系（RBAC + 审批）最全，成本最低、切换最平滑 |
| 中长期 | **独立 IdP**（Keycloak 等开源，或等集团统一身份落地） | 统一身份是基础设施，**不能永久焊死在业务 MES 上**——MES 重构/下线会带走全公司登录 |

**第二决策：时序（比选型更重要）**

认证链路是每个新服务都要接的横切依赖：**SSO 方案应在 Agent / APS 等外围服务落地之前拍板**。现在只有单体，改造成本 ≈ 1；等 Agent、APS、独立看板各接一套登录后再统一，成本 ×N 且必然出现身份碎片化。

**职责边界（关键，最容易做错的地方）**

```
SSO / IdP 只回答「你是谁」（认证 Authentication）
各系统本地 RBAC 回答「你能做什么」（授权 Authorization）——Sa-Token 权限码体系（track:track-in / hold:release…）不变
人员主数据流向：HR / OA → IdP（或 MES 用户表）→ 各系统，单向
```

**技术要点**

- Token 校验：**本地验签**（JWT）或 introspection 结果缓存——禁止每次请求回调 IdP，否则 IdP 成为全局单点
- Agent 服务仍走 D4 契约：service token + 用户身份透传，Tool Facade 侧映射 Sa-Token 权限码（不变）
- 将来 Gateway 引入后，认证可上移网关统一校验——这是「运行单元 ≥4 上 Gateway」的核心收益之一
- 全链路审计：谁、经哪个 IdP、登录了哪个系统、做了什么——与 `mes_tx_log` 审计观对齐

### 5.5 到那时候的形态：选择性治理，不是「切换体系」

```
SSO / IdP（集团 IdP，或过渡期 MES 兼任）
   │ OIDC / CAS · JWT 本地验签
   ▼
[API Gateway 单件] ──► MES 单体 ──┬── Agent 服务（AI）
        │                         ├── APS 服务（计划）
        │                         └── 只读报表 / 看板（按需）
        │ 防腐层 · 事件 + 幂等 + 对账
        ▼
ERP（工单/交期） · OA（审批/人员/待办） · 企微/钉钉（通知）
（各服务自有库；外部系统经 adapter 集成；无分布式事务）
```

| 引入组件 | 时机 | 对应不引入的 |
|----------|------|--------------|
| API Gateway（Spring Cloud Gateway 单件即可） | 运行单元 ≥4，需要统一入口/鉴权/限流 | 注册中心（K8s Service / DNS / Nginx 即可胜任寻址） |
| 统一认证（网关层 JWT 校验） | SSO 拍板 + Gateway 引入后 | 各服务私建用户会话（禁止，见 P8） |
| 链路追踪（SkyWalking / OTel） | 排障需要跨服务 traceId | 配置中心（各服务自管 + 环境变量 + Git） |
| 统一审计 / 对账台 | 多系统合规与财务对齐要求 | 分布式事务框架（业务级幂等 + 对账彻底替代） |
| integration 服务（合并 adapter 们） | 外部系统 ≥3 家 | 每家外部系统一个服务（过度拆分） |

> 换句话说：**Spring Cloud 在本项目里的正确用法是一个「零件库」，不是一个「目的地」。** 到 ERP/OA/APS 接入那天，你从零件库里取的可能只有 Gateway 一个零件。

## 6. 前端形态演进：一个应用 → 单仓库多应用

### 6.1 现状与张力

现状：一个 React 应用双形态（Admin Light / Field Dark 双主题）。这个模式在模块数量少时成立，但 PRODUCT.md 定义的两类用户画像正在**极端分化**：

| 维度 | 管理端 Admin Light | 现场台 Field Dark |
|------|--------------------|-------------------|
| 用户 | 工艺/设备工程师 | 现场操作员（手套/强光） |
| 交互 | 键盘鼠标、表格、抽屉 | 大触控目标、扫码枪、kiosk |
| 环境 | 办公 PC | 车间工控机/平板 |
| 迭代 | 高频加页面 | 求稳，改一处要回归过站全流程 |

张力会随三个事件爆发：① **第三个面出现**（车间大屏看板需要无人值守独立部署）；② **bundle 与发布耦合**（现场台被迫下载管理端全部代码；一次发版全量生效）；③ **AI Copilot / RAG 挂载**（Admin 长出聊天侧栏，Field 明确不要）。

### 6.2 目标形态：单仓库多应用（D11 展开）

```
web/                        # pnpm workspace / Turborepo
  apps/
    admin/                  # 管理端 Admin Light（工程师桌面）
    │   └─ Copilot 侧栏、知识管理后台、AI 客诉包入口
    field/                  # 现场台 Field Dark（操作员大触控）
    │   └─ Track 过站、扫码、Hold、kiosk 全屏
    dashboard/              # 车间大屏（班组长指挥屏）
    │   └─ 只轮询 overview + alarm.active，可独立部署到工控机
  packages/
    ui/                     # 设计系统：Admin Light / Field Dark 两套 token
    api-client/             # REST + WebSocket + SSE 封装（含 Tool Facade 客户端）
    types/                  # 与后端的契约类型（单一来源）
```

**演进节奏（成本递增，按需推进）**：

| 步骤 | 动作 | 成本 |
|------|------|------|
| 1 | **Vite 多入口**：同仓库内按 `admin/` `field/` 物理分包，独立构建产物 | ≈0，随时可做 |
| 2 | pnpm workspace 化：apps/packages 结构，共享依赖提升 | 低，一次迁移 |
| 3 | Turborepo / 构建缓存（可选）：构建变慢后再上 | 按需 |

**触发条件**（见 §4）：大屏看板需要独立部署时，或 Admin/Field 构建发布开始互相拖累时。**现在不急**——单应用双主题还能撑很久，先记住方向即可。

### 6.3 各面前端归属（D13 展开）

| 面 | 归属 | 说明 |
|----|------|------|
| AI Copilot | **MES 前端（Admin 内组件）** | 调 Agent 服务 SSE/REST；全局入口 + Alarm/Hold/Lot 侧栏「问 AI」（RAG 方案 §10 挂载点不变）；**不进 Field 过站路径**（AI 分析 P3） |
| 知识管理后台 | Admin | 权限体系在 MES（`ai:kb:*` 权限码） |
| APS 甘特/负荷编辑器 | **APS 服务自带** | 交互专用密集（拖拽排程），与计划库同源迭代；强行塞进 MES Admin 会造成前后端跨库耦合 |
| 移动端（审批/看板） | **不做原生 App** | OA 待办推送 + 深链回 Web；确有移动刚需再 PWA |
| 车间大屏 | dashboard 应用 | 只读轮询，无人值守 |

### 6.4 现场台的特殊纪律（D14 展开）

- **只读数据可缓存**：断网时可看上次 WIP/队列快照（本地缓存 + 时间戳标注）
- **写操作必须在线**：过站 / Hold / 扫码比对一律在线请求——离线缓冲过站等于把「状态唯一真相」交给了本地存储，禁区
- kiosk 全屏、自动重连、WebSocket 断线自动重订阅；扫码枪按键盘输入设备处理，不引特殊硬件依赖
- Field 发版走独立构建（多入口后天然获得），改 Admin 页面不触碰现场台产物

### 6.5 部署与网络

- 静态产物 Nginx / 对象存储；**同源反代后端**免 CORS；SSE 经反代需 `proxy_buffering off`
- 将来 Gateway 引入后前端零改动：只换 `baseURL`（api-client 统一收口的价值）
- 大屏/现场台部署在车间工控机：版本固定 + 手动升级窗口（不追最新）

## 7. 拆分禁区（红线）

| # | 禁止 | 理由 |
|---|------|------|
| P1 | 拆 Track / Lot / Hold / WIP 到不同进程 | 破坏单库事务闭环与状态唯一真相（§2.2） |
| P2 | Agent / APS / 任何外围服务直连 MES 数据库 | 绕过事务、权限、履历（Agent 规划 P1） |
| P3 | 为「微服务化」引入 Seata/Saga 于过站路径 | 补偿语义与不可逆事务规则冲突 |
| P4 | Agent / APS 以共享 Jar 方式引用 mes.* 领域代码 | 编译期耦合，拆了个寂寞 |
| P5 | 现在就搭 Nacos/网关/链路追踪「备用」 | 无流量的治理组件只有成本，没有收益 |
| P6 | ERP 与 MES 之间上强一致事务（两阶段提交） | 跨自有库系统的正解是最终一致 + 对账（§5.1） |
| P7 | 把 APS 排程调用塞进 Track 过站链路 | 计划是软约束；Track 只消费已发布计划（APS 方案稿 §8） |
| P8 | 外围服务自建用户会话 / 私连用户表 | 认证必须统一（IdP 签发或网关校验），否则身份碎片化、审计断链 |
| P9 | OA / 企微回调不验签、不幂等 | 回调是**不可信外部输入**：可伪造审批、可重复生效 |
| P10 | 把统一身份（IdP 职责）永久焊死在业务 MES 上 | 身份是基础设施；MES 重构/下线会带走全公司登录 |
| P11 | 上微前端（qiankun / Module Federation） | 微前端解决多团队独立发布前端的组织问题；单团队上 = 纯负担，与后端微服务同理 |
| P12 | 现场台离线缓冲写操作（过站/Hold） | 状态真相交给本地存储；与「现场 3 步 Track」产品成功标准冲突 |

## 8. 演进路线

| 阶段 | 形态 | 动作 |
|------|------|------|
| 现在 | 模块化单体 + 单前端应用 | 强化模块纪律（Facade-only + ArchUnit 守护）；前端可先做 **Vite 多入口**分包（成本≈0） |
| +Agent | 单体 + 1 个独立服务 | **先拍板 SSO/IdP 方案**（成本 ≈1，见 §5.4）；Agent 独立仓库；REST Tool Facade + RocketMQ；Docker Compose；Admin 长出 Copilot 侧栏 |
| +ERP / OA | 单体 + 1~2 个运行单元 | `erp-adapter` / `oa-adapter` 先入单体（防腐层 + 本地消息表 + 对账）；MQ 事件 + 幂等消费 |
| +APS | 单体 + 3~4 个运行单元 | APS 独立服务另库**自带甘特前端**；Dispatch 接计划软约束；此时评估 **Gateway 单件**（认证上移） |
| +Adapter/数采 | 单体 + 5~6 个运行单元 | **Gateway + 链路追踪**；外部 adapter 合并 integration 服务；前端按需 pnpm workspace 化 |
| 远期 | 按触发条件 | 见 §4；**可能停在上一格很久，且这是好事** |

> 判断标准始终是：**每个拆出去的进程都要用「省下的协调成本 > 增加的运维成本」自证**；每个引入的治理组件都要用「解决的运维痛苦 > 自身的维护成本」自证。答不上来就不做。

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| 单体腐化为大泥球 | ArchUnit 强制模块依赖规则；Facade 接口评审；表前缀纪律 |
| Agent 单点 | AI 本来就是可降级能力：Agent 不可用时 MES 全功能不受影响（验收标准） |
| 两服务接口漂移 | Tool Facade 接口版本化；契约测试进 CI |
| ERP 对账扯皮 | 本地消息表 + 幂等消费 + 对账台从第一天就建，不靠「以后补」 |
| OA 审批伪造 / 重复生效 | 回调验签 + 幂等 + 审批结果本地落库为准（P9） |
| IdP 单点故障 | 破窗本地账号（仅超管）；JWT 本地验签/缓存，IdP 短暂不可用不放大大面积登录失败 |
| SSO 迁移期身份混乱 | 认证/授权职责分离表（§5.4）；迁移期双轨灰度，按用户组切换 |
| APS 计划与现场脱节 | 强制吃 WIP+设备态快照；短周期滚动重排（APS 方案稿 §8 已定） |
| 双端设计系统漂移 | `packages/ui` 统一两套 token；组件按 Admin/Field 前缀分区 |
| SSE 经反代被缓冲 | Nginx `proxy_buffering off`；api-client 统一封装，不散落各页面 |
| monorepo 化半途而废 | 先 Vite 多入口验证（成本≈0），痛点真实存在再上 workspace |
| 未来真要拆时拆不动 | 拆分预案已存在（§4）；模块边界 = 未来服务边界，这才是模块化单体的真正回报 |
| Python ML 管线引入后失控 | 训练离线化、产物进 MinIO + 模型注册表，推理不依赖 Python 常驻服务 |

## 10. 结论

**架构不是越新越好，是越匹配组织与问题越好。** 当前阶段：模块化单体 + Agent 独立服务，是同时满足「Track 强一致」「AI 快速试错」「单人可运维」三个约束的唯一解。

ERP / OA / APS 加入后也不存在「微服务体系切换」——存在的只是：**ERP / OA 做防腐层集成（最终一致 + 对账，业务真相留在 MES），APS 做同构独立服务（软约束、不挡过站、自带前端），治理组件在运行单元 ≥4 时按需领取。**

SSO 是唯一要求**提前**决策的横切项：趁改造成本 ≈1 时拍板「谁当 IdP」，守住「认证归 IdP、授权留本地、人员主数据单向流」。

前端同理但更温和：**一个仓库、多个应用**——Admin / Field / Dashboard 先构建分离，共享层（ui / api-client / types）沉淀设计系统与契约；不上微前端；现场台写操作永远在线。前端演进的本质和后端一致：**不是推倒重来，是让边界先于结构出现。**
