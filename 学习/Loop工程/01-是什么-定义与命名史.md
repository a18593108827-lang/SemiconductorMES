# 01 · 是什么：定义与命名史

## 1.1 三层定义口径

同一个概念，三个来源给出的定义侧重不同，合起来看最完整：

### ① 提出者口径（Osmani，最精炼）

> **"Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead."**
> （循环工程就是用一个你设计的系统，取代你自己作为那个 prompt Agent 的人。）

配套的一句补充：

> "A loop here can be thought of as a **recursive goal** where you define a purpose and the AI iterates until complete."
> （此处的"循环"可理解为一个**递归目标**：你定义目的，AI 反复迭代直到完成。）

### ② 企业口径（IBM Think，最可操作）

> **Loop Engineering 是设计 agentic workflow（即"循环"）的实践 —— 用最少的 human intervention，迭代式地把 AI Agent 推向完成用户定义的目标。**
> 它不再要求人每一步都给 prompt，而是让 Agent 动态地「行动 → 观察 → 决策 → 迭代」，直到任务完成。

IBM 对这个职业转变的表述值得单独记：

> "For developers, loop engineering reframes their role **away from prompting AI agents toward one in which they design automated systems that prompt, check and guide agents**."
> （开发者的角色从"给 Agent 打 prompt"重新定义为"设计出会自动 prompt、检查、引导 Agent 的系统"。）

### ③ 社区口径（Matt Van Horn《WTF Is a Loop?》，最直白）

> "循环就是你写的**一个小程序**。它替你提示编码 Agent，读取产出结果，判断任务是否完成；如果没完成，就再次提示它。
> **你不再是循环里面那个不断输入提示词的人，你变成了循环的作者，模型变成了子程序。**"

## 1.2 角色转变：驾驶员 → 自动驾驶系统设计师

| | 过去（Prompt-centric） | 现在（Loop-centric） |
|---|---|---|
| 谁在打 prompt | 你，一轮接一轮 | 你设计的系统 |
| 你做的事 | 打字 → 读结果 → 打下一句 | 设计发现/分派/执行/验证/迭代的闭环 |
| 优化对象 | 单条指令的质量 | **生成和验证指令的系统的设计** |
| 人的位置 | 循环**里面** | 循环**上面**（目标设定 + 监督） |
| 类比 | 坐在方向盘后手动控制 | 设计自动驾驶系统 |

**关键：杠杆点移动了，但工作没有变简单。** 它从「对话者」变成了「规则制定者」，对系统设计能力的要求更高，不是更低。

## 1.3 命名史时间线

```
2022  ReAct 论文（Yao et al.，Princeton + Google）
      └─ reason / act / observe 交替 → 成为所有现代 Agent 的基础循环
        ↓
2023  Reflexion（Shinn et al.）
      └─ Actor / Evaluator / Self-Reflection 三分离 + 情节记忆（episodic memory）
         └─ 首次让循环能在单次会话内「自我改进」，且无需重新训练模型
        ↓
2023  AutoGPT 等自主 Agent 实验
      └─ 第一次大规模尝试"让 Agent 自己循环"，但可靠性不足，多数未落地
        ↓
2024.12  Anthropic《Building Effective Agents》
      └─ 提出 evaluator-optimizer（生成+评估循环）与 orchestrator-workers（拆解+分派）
        ↓
2025  工程意识的转折点
      └─ 人们开始有意识地"主动设计 Loop"，而非临时拼 prompt
        ↓
2026.06.07  Addy Osmani 发文命名并系统化「Loop Engineering」★
2026.06.22  O'Reilly Radar 转载
2026.06 同期 Cobus Greyling 开源 cobusgreyling/loop-engineering（CLI 工具化：loop-init / loop-audit / loop-cost）
2026.07.17  IBM Think 发布词条，纳入企业术语体系
```

> **重要认知**：**机制有五年历史，名字只有几个月历史。** 分清这一点，是「真正理解」和「复述热点文章」的分界。

## 1.4 关键澄清：Loop 不是「让 Agent 多跑几轮」

这是社区最大的误解。真正的差别在这五件事：

| 问题 | 一次运行 | 一个 Loop |
|------|---------|----------|
| 为什么开始？ | 你说了算 | 系统按计划/事件触发 |
| 能在哪里动手？ | 不明确 | 显式边界（可读哪些文件、可改哪些模块） |
| 怎么证明做对了？ | 你自己看 | **预定义的 verifier**（类型检查/构建/截图/冒烟测试） |
| 什么时候停？ | 你觉得够了 | **可验证的停止条件** |
| 下次该记住什么？ | 不记 | 决策、阻塞、证据写回外部状态 |

## 1.5 和 cron job 的区别（高频追问）

社区直球问过："这不就是 cron job 吗？" 诚实的回答：

| | 相同点 | 不同点 |
|---|--------|--------|
| **调度层** | 确实就是 cron。Boris Cherny 字面意义上就是用 cron 跑循环 | — |
| **执行层** | — | cron 跑的是**固定脚本**，每一步写死；loop 的**下一步由模型判断** |
| **终止** | — | cron 的结束是时间到了；loop 的结束是**条件被验证为真** |
| **状态** | — | cron 无状态；loop 有 memory/spine，跨运行累积 |

一句话：**cron 是心跳，模型是决策器，verifier 是终点判定。三者合起来才叫 loop。**
