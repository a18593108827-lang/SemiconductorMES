# 02 · 四层演进：Prompt → Context → Harness → Loop

## 2.1 总表

| | ① Prompt | ② Context | ③ Harness | ④ Loop |
|---|---|---|---|---|
| **优化对象** | 怎么问 | 给模型看什么 | 单次运行的环境 | 谁决定何时再 prompt、结果是否合格 |
| **时间** | 2022–2024 | 2025 | 2026 初 | 2026.06 |
| **核心问题** | 一条 prompt 怎么写才好？ | 推理那一刻该看到哪些 token？ | Agent 需要一个什么环境？ | 什么循环让它持续朝目标工作、何时停？ |
| **粒度** | 一句话 | 一堆信息 | 一次运行 | 一串运行 + 状态 |
| **代表** | 提示词技巧、few-shot、CoT | `CLAUDE.md` / `SKILL.md` / `AGENTS.md` / RAG | Claude Code Hooks、沙箱、工具权限 | `/loop`、`/goal`、Automations、Worktrees |
| **天花板** | **再完美的 prompt，也给不了模型它没被告知的事实** | 上下文再多也可能是噪声 | 环境再好，也只覆盖一次运行 | 无人值守的循环也是无人值守地犯错 |

## 2.2 逐层详解

### ① Prompt Engineering（2022–2024）：优化「表达」

技能点是**措辞**：给模型一个角色、把任务拆成步骤、给示例、让它逐步推理。

它优化的是**表达**，天花板很真实 —— **即使 prompt 写得完美，也无法把模型从未获得的事实交给它**。
早期难点：找有效 prompt 靠试错；不同输入下输出一致性难保证。

### ② Context Engineering（2025）：从「词」扩展到「模型看到的一切」

关注点从 prompt 的措辞，扩展到**模型在生成回复那一刻所"看到"的全部信息**：对话历史、检索到的文档、工具输出，以及为该步组装的其他数据。

三个关键定义：

| 谁 | 定义 |
|----|------|
| Tobi Lütke（Shopify，2025 年中） | 提供**一切必要上下文**，让任务处于"可信地可被模型解决"的状态 |
| Andrej Karpathy | 表达了类似框架并获得广泛认可 |
| Anthropic（2025-09 正式化） | **策展并维护**推理时可用的**最优 token 集合** |

> Prompt engineering 由此**变成了 context engineering 的一个组成部分**，不再是独立学科。

### ③ Harness Engineering（2026 初）：优化「单次运行的环境」

当 Agent 开始在真实生产环境做**更长、更自主、多步**的工作，控制机制就成了瓶颈。

**Harness（驾驭层）= 围绕 Agent 的完整运行环境**：

- 支撑它的脚手架（scaffolding）
- 装备给它的工具
- 它必须遵守的显式约束
- 用于**发现并纠正其错误**的反馈回路

它是让 Agent 从「仅仅有能力」变成「真正可依赖」的东西。**Harness 内含 Context，Context 内含 Prompt。**

代表实现：Claude Code 的 Hooks（提交前检查、输出校验、策略强制、自动触发工作流）。

> Hooks 的隐藏收益：**把治理和质量检查从循环内的 Agent 手里拿走**，从而降低 token 成本和算力消耗 —— 用确定性代码做检查，比用模型做检查便宜得多。

### ④ Loop Engineering（2026.06）：优化「循环本身」

它坐在前三层之上，问一个更窄、更**操作性**的问题：

> **什么循环能让 Agent 持续朝目标工作，以及这个循环精确地在什么时候该停？**

**Harness 还在原地，但 Loop 版的 Harness 会**：按表跑（定时器）、生小帮手（子 Agent）、自己喂自己（状态回写）。

## 2.3 为什么要按这四层来记？—— 缺一层会怎样

这是最实用的记忆方式：**每一层对应一类会失效的东西**。

| 缺哪层 | 症状 |
|--------|------|
| 缺 Prompt | 模型不知道你要什么，输出格式乱、无角色 |
| 缺 Context | 模型每次从零猜你的项目；代码风格、约定、历史决策全丢失 |
| 缺 Harness | 单次运行时跑偏：改了不该改的文件、跑了危险命令、没有反馈回路自我纠错 |
| 缺 Loop | 你仍然是人肉中转站 —— 二十分钟后意识到：**"你不是在思考，你是在搬运错误信息"** |

最后那句是社区流传最广的痛点描述，也是 Loop Engineering 要终结的工作方式。

## 2.4 一个关键洞察：为什么是「现在」才火

不是概念突然变聪明了，而是**底层条件在 2026 年中发生了变化**：

| 条件 | 变化 |
|------|------|
| 单次运行能力 | 编码 Agent 已经能**无人值守跑很久**（一小时级、动几十个文件），并能自行从错误中恢复 |
| 瓶颈转移 | 当一次运行能持续一小时，瓶颈不再是「prompt 写得够不够利」，而是**你有没有建一个让它这整小时都保持产出、被检查、且方向正确的循环**——包括没人在看的那部分 |
| 执行成本 | 执行成本已降到可以"直接把所有候选方案都构建出来"，循环化在经济上成立 |
| 工具内建 | 一年前要写一堆 bash 自己维护；**现在六件套直接内置在产品里**（Codex app 与 Claude Code 都有全部五积木） |

> **第三点值得单独记住**：Osmani 说"让我意外的是，这已经不是工具层级的事了"。当能力被产品化，争论"用哪个工具"就没意义了 —— **你只需设计一个无论坐在哪个工具里都能跑的 loop**。

## 2.5 一句话对照

```
Prompt     优化「表达」   —— 你说得不好，模型答不好
Context    优化「输入」   —— 你给得不全，模型只能猜
Harness    优化「环境」   —— 环境不设边界，单次运行就跑偏
Loop       优化「节奏」   —— 没有循环，你就一直当人肉中转站
```
