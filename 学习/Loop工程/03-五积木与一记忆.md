# 03 · 五积木 + 一记忆（组件详解）

> Osmani 的原话：「一个 loop 需要五样东西，再加一个用来记东西的地方。」  
> 下面每一块都按「职责 / 为什么必需 / 两个产品的实现 / 架构注意点」四段来写。

## 3.0 对照表（Codex app 与 Claude Code）

| 积木                       | 在循环里的职责     | Codex app                                                                    | Claude Code                                                 |
| ------------------------ | ----------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Automations**          | 按计划做发现 + 分类 | Automations 标签页：选项目、prompt、频率、运行环境；有发现的进 Triage 收件箱，没发现的自归档；`/goal` 用于"跑到完成" | 计划任务与 cron、`/loop`、`/goal`、hooks、GitHub Actions             |
| **Worktrees**            | 隔离并行的功能开发   | 每个 thread 自带 worktree                                                        | `git worktree`、`--worktree`、子 Agent 的 `isolation: worktree` |
| **Skills**               | 固化项目知识      | Agent Skills（`SKILL.md`），用 `$name` 调用或隐式触发                                   | Agent Skills（`SKILL.md`）                                    |
| **Plugins / Connectors** | 接进你的工具      | Connectors（MCP）+ 用于分发的 plugins                                               | MCP servers + plugins                                       |
| **Subagents**            | 出主意与验证分离    | 以 TOML 定义在 `.codex/agents/`                                                  | `.claude/agents/` 里的 Task 子 Agent、Agent teams               |
| **State / Memory**       | 追踪已完成与待办    | Markdown 或通过 connector 写 Linear                                              | Markdown（`AGENTS.md`、进度文件）或通过 MCP 写 Linear                  |

> **名字略有不同，能力是同一件事。** 一旦发现形状一样，你就不该再为"用哪个工具"争论。

## 3.1 Automations —— 这是心跳

**职责**：**让 loop 成为真正的 loop，而不是"你做过一次的那次运行"。**

**实现要点**：

- Codex app：在 Automations 标签页选**项目 + 要跑的 prompt + 频率 + 跑在本地 checkout 还是后台 worktree**；有产出的运行进 Triage 收件箱，无产出自动归档
- Claude Code：用 `/loop` 按间隔跑，或用 cron 排任务，或用 hooks 在 Agent 生命周期特定点触发 shell，或整个推到 GitHub Actions（合上笔记本也继续跑）
- **Automation 可以调用 Skill** —— 这样你 fire `$skill-name` 而不是把一大段指令粘贴进一个永远不会有人更新的计划任务里（**这是可维护性的关键**）

**OpenAI 内部实际用法**（很朴素但很有说服力）：每日 issue 分诊、汇总 CI 失败、写 commit 简报、抓上周刚被人引入的 bug。

**架构注意点**：Automations 只负责**浮出工作**（surfacing the work），不负责做工作。循环的其余部分才作用于它。

### 会话内的两个关键原语：`/loop` 与 `/goal`

| 原语      | 语义                                                              |
| ------- | --------------------------------------------------------------- |
| `/loop` | **按节奏重跑**                                                       |
| `/goal` | **一直跑到你写的条件为真** —— 且**每一轮之后由一个独立的小模型判断你是否完成**，写代码的 Agent 不给自己打分 |

`/goal` 的例子：给它「`test/auth` 下所有测试通过且 lint 干净」，然后走开。Codex 有同名同语义的原语，支持暂停/恢复/清除。

> **这是整个体系最重要的一个设计**：**把"停止条件"的判定权从执行者手里拿走。** maker 与 checker 的分离，被应用到了"停止"这件事本身上。

## 3.2 Worktrees —— 隔离

**职责**：让两个 Agent 并行工作时不互相踩脚。

**机制**：Git worktree 让多个工作目录共享同一个仓库，从而能并行开分支而**不复制仓库历史**。Agent 在代码被测试通过、被人类 review、或满足其他你设定的条件之前，**不会合并分支**。

**架构注意点**：隔离不只是"避免冲突"，它是**允许并行**的前提。没有隔离，多 Agent 只能串行，成本优势消失一半。

---

## 3.3 Skills —— 知识固化，让意图不再重复付费

**职责**：停止像金鱼一样每个会话重新解释同一个项目背景。

**格式**（两个产品一致）：一个文件夹，内含 `SKILL.md`（指令 + 元数据），可选 `scripts/`、`references/`、`assets/`。

**触发**：Codex 用 `$` 或 `/skills` 显式调用，或在任务匹配 skill 描述时自动触发 —— **这就是为什么"紧凑、朴素"的描述比"聪明"的描述更好**。

**为什么它比看起来重要**：Osmani 在《The Intent Debt》里的论点 —— **Agent 每次会话都是冷的，它会用自信的猜测去填你意图上的任何空洞。** Skill 就是把意图写在外部：约定、构建步骤、"我们不这么做因为出过那次事故"。写一次，agent 每轮都读到。

> **没有 skills，loop 每个周期都把整个项目从零重新推导一遍；有了 skills，它是复利式累积的。**

**两个容易混淆的词**：

- **Skill 是创作格式**（怎么写知识）
- **Plugin 是分发方式**（怎么把 skill 跨仓库共享、把几个打包在一起）

---

## 3.4 Plugins / Connectors —— 触角，让 loop 能真正动手

**职责**：连接你的真实工具。

**机制**：Connectors 构建在 **MCP（Model Context Protocol）** 之上，让 Agent 读 issue tracker、查数据库、打 staging API、往 Slack 发消息。Codex 和 Claude Code 都说 MCP，**所以你为其中一个写的 connector 通常能直接在另一个上用**。Plugins 把 connectors 和 skills 打包，队友一次安装即可，不必凭记忆重建整套配置。

> **这是"只会说会给什么建议的 Agent" 和 "会自己开 PR、关联 ticket、CI 绿了自动在频道里 ping 一下的 loop" 之间的区别。**

**架构注意点**：只看得见文件系统的 loop 是个很小的 loop。Connectors 决定了 loop 能作用于真实环境的**表面面积**。

---

## 3.5 Subagents —— 让出主意的人离检查的人远一点

**职责**：**一个出主意，另一个来检查。**

**为什么必需**：Osmani 的原话很直接 —— **写代码的模型给自己批作业时太宽容了。** 一个带着不同指令（有时还是不同模型）的第二个 Agent，能抓出第一个 Agent 自己说服自己的那些问题。

**实现**：Codex 只在你要求时才起子 Agent，同时跑，然后把结果折回一个答案；用 TOML 定义在 `.codex/agents/`，每个有名字、描述、指令、可选的模型与 reasoning effort —— **所以你的安全审查 Agent 可以是高配置的强模型，而探索 Agent 可以是个快的只读东西**。Claude Code 用 `.claude/agents/` 里的子 Agent 和 agent teams 做同样的事。

**两边常见的分工**：**一个探索、一个实现、一个对照规格验证。**

**在 loop 语境下的特殊价值**：**loop 是在你不看的时候跑的，所以一个你真正信任的 verifier 是你敢走开的唯一理由。** 子 Agent 确实更烧 token（各自跑自己的模型和工具），所以**要花在"第二意见值得付钱"的地方**。

---

## 3.6 State / Memory —— 脊柱

**职责**：追踪项目进展，**防止重复犯错**。

**形态**：Markdown 文件、Linear 看板、任何**活在单次会话之外**、记录"什么已完成、什么下一步"的东西。

**核心原理（值得背下来）**：

> **模型在两次运行之间忘掉一切，所以记忆必须在磁盘上，不能在上下文里。**  
> **The agent forgets; the repo doesn't.**

**为什么它是"脊柱"**：Osmani 举的例子里，状态文件是整个 loop 的支柱 —— **它记住了试过什么、什么通过了、什么还开着，所以明天早上的运行能从今天停下的地方接着走。**

---

## 3.7 把它们串起来：一个完整的 loop 长什么样

Osmani 给的实例形状：

```
① 一个 automation 每天早上在仓库上跑
        ↓
② 它的 prompt 调用一个 triage skill：读昨天的 CI 失败、开着的 issue、最近的 commit
        ↓
③ 把发现写进一个 Markdown 文件或 Linear 看板
        ↓
④ 对每个值得做的发现：开一个隔离 worktree → 派一个子 Agent 起草修复
        ↓
⑤ 第二个子 Agent 对照项目 skills 与现有测试，review 那份草稿
        ↓
⑥ Connectors 让 loop 自己开 PR、更新 ticket
        ↓
⑦ 循环处理不了的，落进 Triage 收件箱给人
        ↓
⑧ 【脊柱】状态文件记住：什么试过、什么过了、什么还开着
        → 明天早上从今天停下的地方继续
```

> **注意你实际上做了什么**：你**设计了一次**。上面那些步骤你**一条 prompt 都没打**。
