# 04 · 架构师视角：把 Loop 当控制系统设计

> 前几篇讲「是什么」。这一篇讲**如果让我来设计，我会怎么想**。所有结论都标注了依据来源；带「推论」的是我的判断而非原文。

## 4.1 第一原则：Loop 是**控制系统**，不是流程编排

我不同意把它理解成"更高级的工作流"。Workflow 编排的是**已知步骤**；Loop 编排的是**未知步骤 + 一个判定器**。所以它和编排系统的架构重心完全不同：

| | Workflow 编排 | Loop 控制系统 |
|---|---|---|
| 核心对象 | 步骤 DAG | **目标 + 判定器 + 状态** |
| 正确性来源 | 流程定义正确 | **验证器能否说"不"** |
| 主要风险 | 某步失败 | 跑偏、不收敛、幻觉成功、成本失控 |
| 可观测重点 | 每步耗时/成功率 | **每一步的证据链 + 终止理由** |

**因此设计 Loop 前必须先能回答三个问题**（答不出来就不该上 loop）：

1. **目标可否被机械化验证？**（有测试/类型检查/构建/截图 diff，还是只有"我觉得行"）
2. **谁判定停止？**（必须是执行者之外的实体）
3. **做错了怎么收拾？**（能否回滚、隔离、限权）

> 第 1 题答"不能"时，Loop 的收益上限就已经锁死了 —— 你只是把"人肉中转站"变成了"自动化的、无人检查的猜测生成器"。

## 4.2 架构上必须先认清的三个失败面

来源：Machine Learning Mastery 对 Loop 工程的分析，这三个是**结构性问题**，不是调参能解决的。

| 失败面 | 机理 | 架构解法 |
|--------|------|---------|
| **① 上下文增长 / 腐烂** | 长循环里每一步都往记录里追加思考、工具输出、错误。不管它，记录要么溢出，要么质量随长度下降 —— **模型对埋在越来越长记录里"真正重要"的东西，关注度会不稳定** | 把 context engineering 用在**循环内部**：把旧步骤压成短摘要、剪掉过期输出、**把子 Agent 隔离到它自己的干净窗口里，只回报结论** |
| **② 终止** | 可以说是**代价最高的一个错误**。没有终止要么永远跑，要么凭一个猜测任意停下 —— 在无人值守的系统里两者都不可接受 | **叠加多个独立出口**（见 4.3） |
| **③ 验证** | 本质是信任问题：**"完成"是一个声明，不是证明** | 建立验证层级（见 4.4） |

**注意 ① 的一个推论**：子 Agent 不只是"多一个视角"，它还是**上下文隔离手段** —— 让侧任务在自己干净的窗口里跑，只把结论带回来。这两个收益要在设计时一起算。

## 4.3 分层退出：四种独立出口必须叠起来

这是我认为 Loop 架构里最值得直接抄的一条：

| # | 出口 | 说明 | 强度 |
|---|------|------|------|
| 1 | **验证器确认目标达成** | verifier 说 pass | 强（但可能被规避，见 4.4） |
| 2 | **迭代次数硬上限** | hard ceiling on iterations | 强（绝对兜底） |
| 3 | **token / 墙钟预算** | 任一超限即退出 | 强（成本兜底） |
| 4 | **无进展检测** | 最近几步产出同样的错误、或状态实质未变 | **最微妙也最容易被漏掉的一条** |

> 四条缺一条，你就有了一类**概率不为零的无限循环**。第 4 条尤其重要，因为它覆盖的是"有动作、有输出、有进展表象，但状态没变"这种最隐蔽的死循环 —— 这也是我在 [ReAct-Agent/09](../ReAct-Agent/09-ReActRuntime参考实现.py) 里专门实现并跑通的那类护栏。

## 4.4 验证层级：确定性 > 模型判断

**黄金标准是确定性验证** —— 测试、类型检查器、编译器、linter。因为它们返回**客观的通过/失败，模型无法用话术绕过**。

**LLM 当裁判更灵活，也真的必要**（有些东西无法机械检查），**但它更容易被"玩游戏"**，而且**让一个模型去评自己产出的工作，是结构上就很弱的检查**。

> **最强的 loop 是这样做的**：只要存在确定性验证器，就**尽量靠它**；只在确实无法量化的那部分任务上，才动用模型判断。

对应到前面 `/goal` 的机制就通了：**每一轮之后由一个独立的小模型判定"是否完成"，而不是写代码的那个 Agent 自己打分 —— maker/checker 分离被应用到了停止条件本身。**

**"Adversarial code review"（对抗式代码审查）** 是同一思想的另一种叫法：审查者要**主动找问题**，而不是确认没问题。

## 4.5 三层节奏：你选哪一层做 Loop，决定了成本和价值

来源：loopengineering.sh 提出的三层循环节奏。**这是我看到的最有架构价值的一个视角。**

| 节奏层 | 周期 | 内容 | 适合谁 |
|--------|------|------|--------|
| **Agentic coding loop** | 秒 → 分钟 | 规划、改代码、跑检查、修订 | 日常编码 Agent 的本职 |
| **Developer feedback loop** | 分钟 → 小时 | review 产品判断、更新规格、决定是否继续 | 工程师 / 技术负责人 |
| **External feedback loop** | 小时 → 周 | 用户反馈、生产数据、市场信号回流到路线图 | 产品 / 团队 |

**架构含义**：
- 越往内层，loop 越便宜、越快、越该自动化
- 越往外层，越贵、越慢、**越需要人的判断**，不该盲目无人值守
- **很多团队的错误是：把外层的东西当内层去做** —— 用自动化循环处理本该由人做产品判断的环节

> 「把反复的、可验证的工作交给 loop，把需要判断力的部分留给工程师。」（51CTO 解读语）

## 4.6 HITL：人在环里的四个检查点

即使最健壮的 loop 也需要人。**这些检查点不是"外挂"，是循环设计的一部分。**

| 层级 | 检查点 |
|------|--------|
| 基础 Agent 循环 | **真正敏感的调用前要求人显式批准** —— 金融交易、数据库写入 |
| 验证循环 | 人**直接充当裁判**（风险太高，不敢只信评分标准时） |
| 输出循环 | 产出**到达终端用户之前**人先批准 |
| Harness 层 | **提议修改 harness 本身**时先评审再上线（改刹车系统必须比开车更谨慎） |

**判断依据**：自动化裁判可以确认"每个链接都能解析""每个测试都通过"，但它**无法察觉**：文档的框架对真正的受众是错的、或者某个动作敏感到来不及等人看就执行了。**这种由上下文、经验、品味构成、很难写成规则的判断，正是人 review 的价值所在。**

## 4.7 成本结构与预算设计

来自多方实测数据（见 [05 · 风险与边界](./05-风险与边界.md) 有完整清单）：

| 结构 | 倍数 |
|------|------|
| 单个 Agent 自主运行 vs 普通聊天 | **≈ 4×** token |
| 多 Agent 构成 | **≈ 15×** token |

**架构结论（推论）**：Loop 的成本不是线性的，是**乘积式放大**的 —— 节奏 × 子 Agent 数 × 每轮上下文长度。所以预算设计必须**先于**能力设计：

1. 先定义**每个 loop 的硬预算**（token / 工具调用 / 墙钟 / 金额）
2. 再定义**降级路径**（预算耗尽时的兜底行为）
3. 再定义**从小规模开始的观察期** —— Osmani 的建议就是：先让它做最朴素的事（每天把 CI 失败分诊进 markdown 文件），**在信任它去开 PR 之前，先看清它的行为**

## 4.8 与 ReAct 的关系（一张表说清）

这是本次调研最该建立的连接 —— **两者不是替代关系，是不同尺度**：

| | ReAct | Loop Engineering |
|---|---|---|
| 尺度 | **单次会话内的循环** | **跨会话、跨运行的循环** |
| 核心单元 | Thought → Action → Observation | 目标 → 发现 → 分派 → 执行 → 验证 → 记忆 |
| 谁提供 prompt | 人在会话里 | **你设计的系统** |
| 状态 | 上下文窗口内 | **磁盘 / 外部看板（spine）** |
| 终止 | `max_steps` / Final Answer | 验证器 + 硬上限 + 预算 + 无进展 |
| 关系 | **是 Loop 的执行内核** | **是 ReAct 外层的编排与治理** |

> 一句话：**Loop Engineering ≈ 把 ReAct 从"一次会话里的循环"提升为"一个有名字、有调度、有验收、有记忆的工程系统"。**
> 所以 [ReAct-Agent](../ReAct-Agent/README.md) 里的护栏（预算/去重/无进展/熔断/HITL）**在这里一个都没作废，只是被放到了更大的循环里。**

## 4.9 落地路线：最小可用 Loop 的四步

**推论**，按风险从低到高排序：

| 步 | 做什么 | 为什么先做这个 |
|----|--------|---------------|
| 1 | 建**状态文件**（spine）：今天做了什么、卡在哪、下一步 | 零风险，且是后续一切的地基 |
| 2 | 建 **verifier**：把已有测试/构建/lint 接成一条命令，明确"绿=完成" | **没有它，后面全是赌博** |
| 3 | 上**最小 automation**：每天早上做一次只读的发现与分诊，产出写进状态文件 | 只读 = 不可能造成破坏，可以放心观察行为 |
| 4 | 才引入**写操作 + 子 Agent 分离 + worktree 隔离** | 此时你已有信任基础和回滚能力 |

**反例警示**：跳过第 2 步直接上第 4 步，等于把"无人值守地犯错"制度化。

## 4.10 映射到本项目（MES）：哪半已经具备

据项目 `AGENTS.md` 与现有文档体系核对，**Loop 最难的那一半其实已经具备**：

| Loop 组件 | 本项目现状 | 判断 |
|-----------|-----------|------|
| **Context 层** | `AGENTS.md`（会话第一入口）+ `docs/` 分层 + frontmatter 六字段 + `INDEX.md` 总账 | ✅ **已是标准 context engineering 落地**，且做了"只加 frontmatter 不动正文"的存量兼容 |
| **Skill 层** | 用户级 skill `ai-native-sdlc`（bootstrap / enforce 双模式） | ✅ 有，且是"意图写在外部"的典型形态 |
| **Harness 层** | plan 未批不动码（A2）、CI 三闸门（后端测试 / 文档 reindex 零 diff / 前端 tsc+test）、每起事故产一条 EVAL | ✅ 治理与反馈回路都在 |
| **确定性 Verifier** | **CI 三闸门就是** —— 客观通过/失败，模型无法绕 | ✅ **这是 Loop 落地最贵也最难的一环，本文框架里属"黄金标准"，已就位** |
| **State / Spine** | `docs/架构/MES-实施进度与下一步.md` + 各模块「已完成功能」+ plan 实施记录 + 每日 memory 日志 | 🟡 **形态齐了**，但靠人工维护，不是 loop 自动回写 |
| **Automations** | 无定时/事件触发的自动化 | ❌ 缺 |
| **Worktrees 隔离** | 未使用 | ❌ 缺 |
| **Subagents（maker/checker 分离）** | 审查与实现目前由同一 Agent 承担 | ❌ 缺（这是"plan 定稿≠正确"这条教训的结构性根源） |
| **`/goal` 式跑到达标** | 无（"测试全绿才算完成"目前靠人判定并记录） | ❌ 缺 |

**推论：如果要补，风险最低、收益最直接的三条**（都不涉及动业务代码）：

1. **把 spine 自动化**：一个只读 automation，每天扫 `docs/eval/` 里未闭环的 EVAL、`status: draft` 超期的 plan、`INDEX.md` 里状态列与正文不一致的文档 → 分诊结果写进一个 markdown 文件。**纯只读，零破坏风险。**
2. **子 Agent 分离**：把"审查"从实现 Agent 手里拿出来，交给一个独立 Agent。项目已有的教训（`plan 定稿 ≠ plan 正确`、多轮审查须落代码行号证据）**正是因为"自己给自己批作业"太宽容**，这与 4.4 的判断完全一致。
3. **给现有 CI 加一个"跑到达标"的语义**：把 `.github/workflows/ci.yml` 三闸门从"推一次跑一次"升级为"未通过则持续修复直到通过"的循环 —— 也就是给已有的确定性 verifier 配上 `/goal`。

> **一句话结论**：这个项目已经完成了 Loop Engineering 里**最容易做错的 Prepare 部分**（context + harness + verifier）。真正缺的是**循环本身**（automation / goal / 隔离 / 分审），而补齐的风险远低于从零开始的团队。
