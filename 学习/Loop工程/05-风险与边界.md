# 05 · 风险与边界：它不一定对

> 这一篇存在的理由：这个概念**只有几个月历史**，提出者 Osmani 自己就写了 ——
> *"However, it's still early; **I'm skeptical**, and you absolutely have to be careful about token costs."*
> 而社区的推背感远远超过了当时已有的平衡视角。所以先把代价讲清楚。

## 5.1 五大失败模式（架构上必须预设）

| 失败模式 | 机理 | 典型表现 |
|---------|------|---------|
| **上下文溢出与腐烂** | 窗口被填满，输出质量下降，**没有任何明显报错** | 循环看起来在正常工作，产出却越来越水 |
| **无进展循环** | Agent 无限重复同一个失败动作 | 同一工具同参数反复调用 |
| **目标错配 / 奖励黑客**（reward hacking） | loop 优化的是**可检查的代理指标**，而非真实目标 | **教科书案例：Agent 把失败的测试删掉，让 CI 变绿** |
| **幻觉成功** | Agent 宣称完成，背后没有任何真实验证 | "已完成，测试通过"（其实没跑） |
| **成本爆炸** | 长循环静默烧掉远超任务所需的 token | 账单异常，而任务本身很轻 |

> **这五个的共同解法是同一个**：在循环里放一个**真实的、外部的、确定性的检查** —— 不是 Agent 自己的话。

## 5.2 成本有多贵（实测数据）

| 场景 | 数据 |
|------|------|
| 单个 Agent 自主运行 | 约普通聊天用量的 **4×** token |
| 多 Agent 构成 | 约 **15×** token |
| 极端案例 | Peter Steinberger 承认有段时间**每月用掉约 130 万美元**的 token |
| 事故案例 | 有报告称一个循环在 **5 分钟内调用同一个坏掉的工具 400 次** |

**注**：4×/15× 出自某解读文章的试算，非厂商官方口径，但量级足以说明问题。

**推论**：**"循环能推多远，直接取决于预算。"** 模型厂商的"无限 token"方案与开发者的 Pro 计划限额之间存在现实落差 —— 这一点在做技术选型时必须先算清楚，而不是先设计再发现付不起。

## 5.3 三种"债"：比技术债更隐蔽

这是 IBM 与 Osmani 都强调的一组概念，**值得单独记**：

| 债 | 定义 | 为什么危险 |
|----|------|-----------|
| **技术债**（传统） | 有意走捷径留下的 | 已知，可规划偿还 |
| **理解债**（comprehension debt） | **系统里代码总量** 与 **人类理解程度** 之间的**差距** | **被动累积**：Agent 写得越快、人查得越少，差距越大；而且**常常是静默的** —— 因为代码通过了自己的自动化测试。等到必须排查生产故障、做重大改动、或响应事故时才发现 |
| **意图债**（intent debt） | **解释系统"为什么这么做"的具体理由的丢失** | 不写进 `AGENTS.md` / `SKILL.md`，Agent 只能靠猜；结果它可能为了错误的目标做优化 —— **技术上无懈可击，但和项目目标背道而驰** |

**关键区别**：技术债来自**有意的捷径**；理解债是**被动的、快速累积的、常常静默的**。

## 5.4 认知投降（cognitive surrender）

| 概念 | 含义 |
|------|------|
| **认知卸载**（offloading） | 把产出交给 AI，但由人验证 —— **健康** |
| **认知投降**（surrender） | **完全放弃控制** —— 开发者不加质疑地接受循环的产出 |

**Osmani 的警告值得原样引用**：

> **"带着判断去设计 loop 是解药；为了逃避思考去设计 loop 是助燃剂。"**
> **"两个人可以建出完全相同的 loop，却得到相反的结果 —— loop 不知道区别。你知道。"**

## 5.5 它**不**是什么（"What Loop Engineering Is Not"）

社区在头几周里炒得比平衡视角跑得快，所以官方解读专门列了反面：

1. **不是每个开发者下周二就得跑自主 Agent 舰队。**
2. **对真正一次性（one-off）的任务，一次交互式会话往往更快、更安全** —— 为它专门工程化一个完整 loop，是把 loop engineering 的适用范围读错了。
3. **loop 不把人从判断中移除。** 只是判断的位置变了：从循环内部移到了循环设计之上。

## 5.6 最重要的一条反驳（来自社区高赞回应，值得单独记）

> **设计 loop 只是工作的一半。另一半是在 loop 里放进能说「不」的东西 —— 测试、类型检查、真实的错误。**
> **没有反向推力的循环，只会变成 AI 不断同意自己的装置。**

这句话我认为比"五积木"更重要。它把 Loop Engineering 从"自动化方法论"拉回到"**你必须在系统里嵌入一个不会讨好 AI 的裁判**"。

配套的一句（Osmani）：

> **"无人值守地跑的 loop，也是无人值守地犯错的 loop。"**
> **"完成是一个声明，不是一个证明。"**

## 5.7 什么时候**不该**用 Loop

| 场景 | 为什么不该 |
|------|-----------|
| 一次性任务 | 交互式会话更快、更安全；loop 的工程开销不划算 |
| 目标无法机械化验证 | 你只是把猜测自动化了，且无人纠正 |
| 不可逆的高风险动作 | 除非加了 HITL 与回滚 |
| 预算受限（token-poor） | 使用模式在 token 富裕/匮乏下差异极大，5.2 的倍数会直接压垮你 |
| 团队还没有 verifier | 先有验证，再有循环（见 [04 · 落地路线](./04-架构师视角.md#49-落地路线最小可用-loop-的四步)） |
| 你打算用它来逃避思考 | 这是助燃剂，不是解药 |

## 5.8 三条止血规则（推论 + 原文建议）

1. **先算钱，再上循环**：每个 loop 定义硬预算（token / 工具调用 / 墙钟 / 金额）+ 降级路径。
2. **从小做起、看清行为再授权**：Osmani 的建议 —— 从"每天早上把 CI 失败分诊进 markdown"这种**只读**的事开始，**在信任它去开 PR 之前，先看清它的行为**。
3. **坚持读它写的东西**：理解债的解法只有两个 —— 读产出，或者限制产出速度。**没有第三条路。**

## 5.9 平衡结论（我的判断）

| 该信的部分 | 该警惕的部分 |
|-----------|-------------|
| 它是**真实存在的工程范式转移**，不是纯炒作 —— 四层演进的因果链清晰，且两个主流产品已内建全部原语 | 名字很新（2026.06），**长期有效性尚无足够数据**，提出者本人存疑 |
| "把反复的、可验证的工作交给 loop，把判断留给工程师"这个**分工原则**是稳的 | "所有开发都该 loop 化"是错的 —— 它明确不适用于一次性任务 |
| 五积木 + 一记忆这个**组件清单**有实操价值，且可跨工具复用 | 成本是**乘积式放大**的，财务风险真实（4× / 15× / $1.3M 月） |
| **验证必须确定性优先**这条是硬约束 | 若验证责任被默认转移给 loop，理解债与认知投降会静默累积 |

> **一句话**：**Loop Engineering 放大你已有的判断力 —— 好的和坏的都放大，而且你盯着的时间更少。**
> Osmani 的收尾语最准确：**"搭好你的 loop，但要像一个打算继续当工程师的人那样搭它。"**
