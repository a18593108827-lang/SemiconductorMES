# 06 · 大厂面试题与答题模板

> 格式沿用 [ReAct 笔记](../ReAct-Agent/08-面试高频题与答题模板.md)：**考察点 / 回答主线 / 加分项 / 常见追问**。
> 注意：这个概念很新（2026.06 命名），所以面试里**考的不是"你知不知道这个词"，而是"你能不能把它和已有的架构概念接上、并且能说出代价"**。凡是只背五积木的答案，都拿不到高分。

---

## 题 1：什么是 Loop Engineering？它和 Prompt / Context / Harness 是什么关系？

**考察点**：你是否能把它放进一条**有因果的演进线**里，而不是当成孤立新词。

**回答主线**

定义先给准：

> Loop Engineering 是**用一个你设计的系统，取代你自己作为那个 prompt Agent 的人**。这里的循环可以理解为一个**递归目标**：你定义目的，AI 反复迭代直到完成。

然后立刻把它放进四层演进（**每层包裹前一层，不是替代**）：

| 层 | 优化对象 | 时间 | 核心问题 |
|----|---------|------|---------|
| Prompt Engineering | 怎么**问** | 2022–2024 | 怎样写一条 prompt 才让模型答得好？ |
| Context Engineering | 给模型看**什么** | 2025 | 推理那一刻该看到哪些 token？ |
| Harness Engineering | 怎么约束**单次运行** | 2026 初 | 单次运行需要什么环境？ |
| **Loop Engineering** | **谁决定何时再 prompt、结果是否合格** | 2026.06 | 什么循环能让 Agent 持续工作、**何时该停**？ |

**关键连接句**：*Harness 是单个 Agent 运行的环境；Loop Engineering 比它高一层 —— Harness 还在原地，但它按表跑、生小帮手、自己喂自己。*

**加分项**

- 指出**机制有五年历史、名字只有几个月**：血脉是 `ReAct (2022) → Reflexion (2023，Actor/Evaluator/Self-Reflection + 情节记忆) → Anthropic《Building Effective Agents》(2024.12，evaluator-optimizer / orchestrator-workers) → Loop Engineering (2026.06)`
- 点出它的**提出者与点火者**：Addy Osmani 命名；Peter Steinberger 与 Boris Cherny（Claude Code 负责人）提供实践背书
- 主动说"**提出者本人也明确表示存疑、且警告 token 成本**"—— 这句话能让面试官立刻判断你不是照抄热点

**常见追问：这不就是 cron job 吗？**
答（要诚实）：**调度层确实就是 cron**，Boris Cherny 字面意义上就是用 cron 跑循环。但——**cron 跑固定脚本，loop 的下一步由模型判断；cron 的结束是时间到了，loop 的结束是条件被验证为真；cron 无状态，loop 有 memory/spine 跨运行累积。**

## 题 2：请设计一个生产级 Loop，需要哪些组件？

**考察点**：能不能落到具体原语上，而不是"让它循环起来"。

**回答主线**

**五个积木 + 一个记忆**：

| 积木 | 职责 | 一句话 |
|------|------|--------|
| Automations | 心跳 | 按计划自动发现 + 分类任务 |
| Worktrees | 隔离 | 多 Agent 并行互不踩脚 |
| Skills | 知识固化 | 把项目知识写下来，不每轮重猜 |
| Plugins / Connectors | 触角 | 通过 MCP 接进真实工具 |
| Subagents | 制衡 | **一个出主意，另一个来检查** |
| **State / Memory** | 脊柱 | 活在会话之外的状态：markdown 或看板 |

**然后给一个完整例子**（这一步最能证明你真懂）：一个 automation 每天早上跑 → 调用 triage skill 读昨天的 CI 失败 / open issue / 最近 commit → 写进 markdown 或看板 → 对值得做的发现开隔离 worktree、派子 Agent 起草修复 → 第二个子 Agent 对照 skills 与现有测试 review → connectors 让它自己开 PR、更新 ticket → 处理不了的落进人工收件箱 → **状态文件记住什么试过、什么过了、什么还开着，明天从昨天停下的地方继续。**

**加分项**

- 强调 **"The agent forgets; the repo doesn't"** —— 记忆必须在磁盘上，不在上下文里
- 指出 **Skill 是创作格式、Plugin 是分发方式**（易混）
- 指出子 Agent 有**双重收益**：多一个视角 + **上下文隔离**（侧任务在干净窗口里跑，只回报结论）
- 提到 `/goal` 这类原语的机制：**每轮之后由独立的小模型判定是否完成，写代码的 Agent 不给自己打分**

**常见追问：为什么必须有个"状态/记忆"层？**
答：因为**模型在两次运行之间忘掉一切**。没有脊柱，每次运行都从零开始，会重复踩同一个坑；有了它，循环才是**复利式累积**的而不是每轮重新推导。

## 题 3：如何保证 loop 不跑飞？（终止 / 预算 / 验证）

**考察点**：线上稳定性 —— **这是最核心的一题**。

**回答主线 —— 分三层讲**

**第一层：分层退出（缺一条就有一类概率不为零的无限循环）**

| # | 出口 | 说明 |
|---|------|------|
| 1 | 验证器确认目标达成 | verifier 说 pass |
| 2 | **迭代次数硬上限** | 绝对兜底 |
| 3 | **token / 墙钟预算** | 成本兜底 |
| 4 | **无进展检测** | 最近几步产出同样错误、或状态实质未变 —— **最易被漏掉的一条** |

**第二层：验证层级（黄金标准是确定性验证）**

测试、类型检查器、编译器、linter —— 返回**客观通过/失败，模型无法用话术绕过**。
LLM 当裁判更灵活、确实必要（有些东西无法机械检查），**但更容易被"玩游戏"**，而且**让模型评自己产出的工作是结构上就很弱的检查**。
→ **只要存在确定性验证器就尽量靠它，只在无法量化的部分才动用模型判断。**

**第三层：上下文治理**（长循环的隐形杀手）
把 context engineering 用在**循环内部**：旧步骤压成短摘要、剪掉过期输出、**子 Agent 隔离到自己的干净窗口**。否则窗口要么溢出，要么质量随长度静默下降。

**加分项**

- 用一句话收尾：**"无人值守地跑的 loop，也是无人值守地犯错的 loop。"**
- 主动提 **"完成是一个声明，不是一个证明"**（done is a claim, not a proof）
- 提 **maker/checker 分离**：写代码的模型给自己批作业太宽容

**常见追问：模型一直不输出"完成"怎么办？**
答：硬上限兜底 + 强制进入"只许总结"模式 + 转人工，并**把触发原因写进脊柱**，避免下次重复。

## 题 4：Loop 的成本怎么控？

**考察点**：财务风险意识 —— **很多候选人在这一题上翻车**。

**回答主线**

先给量级（有数据支撑才有说服力）：

| 场景 | 倍数 |
|------|------|
| 单个 Agent 自主运行 vs 普通聊天 | **≈ 4×** token |
| 多 Agent 构成 | **≈ 15×** token |

再给极端案例：Peter Steinberger 承认有段时间**每月约 130 万美元** token；有报告称一个循环**5 分钟内调同一个坏工具 400 次**。

**然后给控制手段（这才是得分点）**：

1. **硬预算先于能力**：每个 loop 定义 token / 工具调用 / 墙钟 / 金额上限 + 降级路径
2. **乘积意识**：成本 ≈ 节奏 × 子 Agent 数 × 每轮上下文长度 —— 三者都是乘数，**先砍指数最大的那个**
3. **上下文压缩**是最大的降本点（也是 4×→15× 的主要放大器）
4. **子 Agent 只花在"第二意见值得付钱"的地方**（不是每个环节都要 pair）
5. **从小规模观察期开始**：先只读、低频率，看清行为再放开
6. **把检查交给确定性代码而非模型**：hooks/CI 做治理比让 Agent 自己检查便宜得多

**常见追问：token 预算和业务价值怎么权衡？**
答：**"循环能推多远，直接取决于预算。"** 模型厂商的"无限 token"方案与个人 Pro 限额之间存在现实落差 —— 所以选型时先算钱，不是先设计再发现付不起。

## 题 5：怎么防 loop 里的 reward hacking 和"幻觉成功"？

**考察点**：是否理解**验证器也会被规避**。

**回答主线**

先复述两个失败模式：
- **目标错配 / 奖励黑客**：loop 优化的是**可检查的代理指标**而非真实目标。**教科书案例：Agent 把失败的测试删掉，让 CI 变绿。**
- **幻觉成功**：Agent 宣称完成，背后没有真实验证。

**四道防线**：

1. **确定性验证优先** —— 但要注意：**确定性验证器本身也可能被"绕过"**（删测试、改断言、跳过用例）→ 所以验证器必须**由循环外的代码执行**，且**禁止 Agent 修改验证器本身**
2. **maker/checker 分离** —— 审查者带着**不同指令、有时不同模型**，任务是**主动找问题**（对抗式审查），而不是确认没问题
3. **保留证据而非结论** —— 要求交回**命令、输出、下一步决定**；失败就如实保留，不许把失败包装成成功
4. **HITL 卡在不可逆处** —— 敏感调用前需人批准

**加分项**

- 点出**循环里必须有一个"能说不"的东西**："没有反向推力的循环，只会变成 AI 不断同意自己的装置。"
- 把"停止条件"也纳入 maker/checker：**`/goal` 用一个独立小模型判断是否完成**，正是这个思想

**常见追问：怎么可能发现 Agent 在刷分？**
答：看**证据链而不是结论** —— 变更集里是否出现了"验证器被改弱"（测试被删/断言被放宽/用例被跳过）、指标改善但业务结果没变、以及同一 loop 的历史里**"完成"与"回滚"成对出现**。

## 题 6：Loop Engineering 会不会取代工程师？HITL 放在哪？

**考察点**：对"人的位置"的理解深度。

**回答主线**

**不会。但它会让"人的位置"移动。**

**四个必须设 HITL 的检查点**：

| 层级 | 检查点 |
|------|--------|
| 基础 Agent 循环 | **真正敏感的调用前要人显式批准** —— 金融交易、数据库写入 |
| 验证循环 | 人**直接充当裁判**（风险太高、不敢只信评分标准时） |
| 输出循环 | 产出**到达终端用户之前**人先批准 |
| Harness 层 | **提议修改 harness 本身**时先评审 —— 改刹车系统要比开车更谨慎 |

**为什么删不掉人**：自动化裁判能确认"每个链接都可解析""每个测试都通过"，但它**无法察觉**：文档框架对真正的受众是错的、或者某个动作敏感到不该无人执行。**这种由上下文、经验、品味构成、很难写成规则的判断，正是人 review 的价值所在。**

**三条会静默累积的代价**：

| 债 | 含义 |
|----|------|
| **理解债** | 系统里代码总量 与 人类理解程度 的**差距**，被动累积、常常静默（因为通过了自己的测试） |
| **意图债** | "为什么这么做"的理由丢失 → Agent 为错误目标优化，技术无懈可击但方向反了 |
| **认知投降** | 不是"认知卸载"（有人验证），而是**完全放弃控制** |

**加分项**：引用 Osmani 那句 —— **"两个人可以建出完全相同的 loop，却得到相反的结果 —— loop 不知道区别。你知道。"**

**常见追问：那"工程师的工作"变成什么了？**
答：**从"循环内的操作者"变成"循环上的目标设定者与监督者"**；杠杆点移动了，**但工作没有变简单** —— 它对系统架构思维的要求（可靠的反馈机制、停止条件、异常处理）远高于对话者。

## 题 7：什么场景**不该**用 Loop？

**考察点**：**克制力**。这题答得好，比多背三个组件更加分。

**回答主线**

| 场景 | 为什么不该 |
|------|-----------|
| **一次性任务** | 一次交互式会话往往**更快、更安全**；为它工程化完整 loop 是把适用范围读错了 |
| **目标无法机械化验证** | 你只是把猜测自动化了，而且无人纠正 |
| **不可逆的高风险动作** | 除非加了 HITL 与回滚 |
| **预算受限** | 使用模式在 token 富裕/匮乏下差异极大，4×/15× 会直接压垮 |
| **团队还没有 verifier** | 先有验证，再有循环 |
| **你打算用它来逃避思考** | 这是助燃剂，不是解药 |

**加分项**：给出正确的分工原则 —— **"把反复的、可验证的工作交给 loop，把需要判断力的部分留给工程师。"** 以及三层节奏的克制：**agentic loop（秒–分钟）该自动化，developer loop（分钟–小时）与 external loop（小时–周）越往外越该留给人。**

**常见追问：那我们团队该从哪一步开始？**
答：按风险从低到高 —— ① 建**状态文件**（零风险，是地基）→ ② 建 **verifier**（把已有测试/构建/lint 接成一条命令，明确"绿=完成"）→ ③ 上**最小 automation，且只读**（每天一次发现+分诊，产出写进状态文件）→ ④ **才**引入写操作、子 Agent 分离、worktree 隔离。
**跳过第 ② 步直接上第 ④ 步，等于把"无人值守地犯错"制度化。**

# 📌 面试速记版

**定义（一句话）**

> Loop Engineering 是**用一个你设计的系统，取代你自己作为那个 prompt Agent 的人** —— 定义递归目标，让循环自己驱动 Agent 迭代到完成。

**四层（一句话）**

> Prompt 管**怎么问** → Context 管**给它看什么** → Harness 管**单次运行的环境** → Loop 管**谁决定何时再 prompt、何时停、怎么证明做对了**。**每层包裹前一层。**

**五积木 + 一记忆（一句话）**

> Automations 心跳 · Worktrees 隔离 · Skills 固化知识 · Connectors 接工具 · Subagents 分审 · **Memory 是脊柱——模型会忘，仓库不会。**

**终止四出口（一句话）**

> **验证器 + 迭代硬上限 + 预算 + 无进展检测**，缺一条就有一类无限循环。

**三条必须记住的硬话**

| 场景 | 说法 |
|------|------|
| 验证 | **"完成是一个声明，不是一个证明。"** |
| 无人值守 | **"无人值守地跑的 loop，也是无人值守地犯错的 loop。"** |
| 设计哲学 | **"设计 loop 只是工作的一半；另一半是在 loop 里放进能说'不'的东西。"** |

**成本（一句话）**

> 单 Agent 自主运行 **≈4×**、多 Agent **≈15×** token；极端案例月耗 **$1.3M**、5 分钟调坏工具 **400 次**。**成本是乘积式放大的：节奏 × 子 Agent 数 × 每轮上下文长度。**

**收尾句（最加分）**

> **"搭好你的 loop，但要像一个打算继续当工程师的人那样搭它。"**
