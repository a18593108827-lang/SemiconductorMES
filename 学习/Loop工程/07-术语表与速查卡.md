# 07 · 术语表与速查卡

## 7.1 术语中英对照

| 中文 | 英文 | 含义 |
|------|------|------|
| 循环工程 | **Loop Engineering** | 本笔记主题：设计自动 prompt/检查/引导 Agent 的闭环系统 |
| 递归目标 | recursive goal | 每轮迭代都重新评估的目标 + 可验证的停止条件 |
| 提示工程 | Prompt Engineering | 优化「怎么问」（2022–2024） |
| 上下文工程 | Context Engineering | 优化「给模型看什么」（2025） |
| 驾驭工程 | **Harness Engineering** | 优化「单次运行的环境」：脚手架、工具、约束、反馈回路（2026 初） |
| 驾驭层 / 马具 | harness | 围绕 Agent 的完整运行环境 |
| 自动化 | automations / scheduling | 循环的心跳：按计划/事件触发 |
| 工作树 | **worktrees** | Git 机制：多工作目录共享一个仓库，用于并行隔离 |
| 技能 | **skills** | `SKILL.md` 形式的任务级项目知识 |
| 连接器 | connectors（基于 **MCP**） | 把 Agent 接进真实工具（issue、DB、Slack、API） |
| 插件 | plugins | skill + connector 的**打包分发**方式 |
| 子代理 | **subagents** | 分派专用角色；核心用途是 maker/checker 分离 |
| 制作者 / 检查者 | **maker / checker** | 一个出主意、另一个来检查 |
| 脊柱 / 状态层 | **spine** / state / memory | 活在会话外部的持久状态（markdown 或看板） |
| 收件箱 | triage inbox | 自动化运行中有产出的结果所汇入的人工待办 |
| 目标命令 | `/goal` | 跑到"可验证停止条件"为真；由**独立小模型**判定是否完成 |
| 循环命令 | `/loop` | 按节奏重跑 |
| 验证器 | verifier | 独立的检查机制（测试/类型检查/构建/截图/冒烟） |
| 确定性验证 | deterministic verification | 客观 pass/fail，模型无法用话术绕过 —— **黄金标准** |
| 对抗式审查 | adversarial review | 审查者主动找问题，而非确认没问题 |
| 分层退出 | layered exits | 验证器 + 硬上限 + 预算 + 无进展检测，四条独立叠加 |
| 无进展检测 | no-progress detection | 状态实质未变即判无进展 |
| 奖励黑客 | **reward hacking** | 优化可检查的代理指标而非真实目标（删测试让 CI 变绿） |
| 幻觉成功 | hallucinated success | 宣称完成而背后无真实验证 |
| 上下文腐烂 | context rot | 窗口变长导致输出质量静默下降 |
| 理解债 | **comprehension debt** | 代码总量 与 人类理解程度 的差距，被动累积 |
| 意图债 | **intent debt** | "为什么这么做"的理由丢失 |
| 认知投降 | **cognitive surrender** | 完全放弃控制（区别于"认知卸载"） |
| 人在环 | HITL | 敏感动作前的人工确认 |
| 三层节奏 | three loop cadences | agentic（秒–分）/ developer（分–时）/ external（时–周） |

## 7.2 四层演进速查

| 层 | 优化对象 | 时间 | 缺了会怎样 |
|----|---------|------|-----------|
| ① Prompt | 怎么**问** | 2022–2024 | 模型不知道你要什么 |
| ② Context | 给模型看**什么** | 2025 | 模型每轮从零猜你的项目 |
| ③ Harness | 单次运行的**环境** | 2026 初 | 单次运行跑偏、无反馈回路 |
| ④ Loop | **谁决定何时再 prompt** | 2026.06 | **你一直是人肉中转站** |

## 7.3 五积木 + 一记忆速查

```
Automations  心跳    按计划发现 + 分类，产物进 triage 收件箱
Worktrees    隔离    并行不踩脚，未经验证不合并
Skills       知识    写一次，agent 每轮都读到（意图写在外部）
Connectors   触角    基于 MCP 接进真实工具
Subagents    制衡    一个出主意，另一个来检查
Memory       脊柱    活在会话外；模型会忘，仓库不会
```

**易混**：Skill = 创作格式；Plugin = 分发方式。

## 7.4 终止四出口（背下来）

```
① 验证器确认目标达成        ← 达标退出
② 迭代次数硬上限            ← 绝对兜底
③ token / 墙钟 / 金额预算    ← 成本兜底
④ 无进展检测                ← 最易被漏掉的一条
```

## 7.5 五大失败模式

| 失败模式 | 一句话 |
|---------|--------|
| 上下文溢出 / 腐烂 | 窗口填满，质量静默下降，无报错 |
| 无进展循环 | 无限重复同一个失败动作 |
| 奖励黑客 | 删掉失败的测试让 CI 变绿 |
| 幻觉成功 | 声称完成，无验证 |
| 成本爆炸 | 静默烧掉远超任务所需的 token |

> **共同解法**：循环里放一个**真实的、外部的、确定性的检查** —— 不是 Agent 自己的话。

## 7.6 三层节奏与人的位置

| 节奏 | 周期 | 该谁管 |
|------|------|--------|
| Agentic coding loop | 秒 → 分钟 | **该自动化** |
| Developer feedback loop | 分钟 → 小时 | **该留给人判断** |
| External feedback loop | 小时 → 周 | **该留给人决策** |

> 常见错误：**把外层的事当内层做** —— 用自动化循环处理本该由人做的产品判断。

## 7.7 落地决策树

```
这个任务值得建 loop 吗？
├── 是一次性任务？ ──▶ 用交互式会话（更快更安全），别建 loop
└── 会反复发生？
     ├── 目标能被机械化验证吗？
     │    ├── 不能 ──▶ 先解决验证，否则你只是把猜测自动化了
     │    └── 能 ──▶ 继续
     └── 有不可逆的高风险动作吗？
          ├── 有 ──▶ 该步骤必须加 HITL + 回滚
          └── 没有 ──▶ 按此顺序落地：
                       ① 建状态文件（spine，零风险）
                       ② 建 verifier（"绿=完成"）
                       ③ 上只读 automation（看清行为）
                       ④ 才引入写操作 + 子 Agent 分离 + worktree
```

## 7.8 三条必须记住的原话

| 场景 | 原话 |
|------|------|
| 验证 | **"完成是一个声明，不是一个证明。"**（done is a claim, not a proof） |
| 无人值守 | **"无人值守地跑的 loop，也是无人值守地犯错的 loop。"** |
| 最重要的反驳 | **"设计 loop 只是工作的一半。另一半是在 loop 里放进能说'不'的东西 —— 测试、类型检查、真实的错误。没有反向推力的循环，只会变成 AI 不断同意自己的装置。"** |
| 收尾 | **"搭好你的 loop，但要像一个打算继续当工程师的人那样搭它。"** |

## 7.9 与 ReAct 的边界（一句话）

> **ReAct 是循环的执行内核（单次会话内，Thought→Action→Observation）；Loop Engineering 是它的外层工程系统（跨会话、有调度、有验收、有记忆）。**
> ReAct 里的护栏（预算 / 去重 / 无进展 / 熔断 / HITL）在 Loop 里**一个都没作废**，只是被放进了更大的循环。
