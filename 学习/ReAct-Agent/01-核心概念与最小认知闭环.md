# 01 · 核心概念与最小认知闭环

## 1.1 定义

ReAct 不是一个 Prompt 技巧，而是**一种 Agent Runtime 的控制模式**：

> 让 LLM 在「推理 → 行动 → 观察 → 再推理」的闭环中，动态调用工具、获取外部事实，直到完成任务。

出处：Google/Princeton 论文《ReAct: Synergizing Reasoning and Acting in Language Models》。
核心就是 **Thought → Action → Observation** 循环。

对比理解：

| 模式 | 特点 | 短板 |
|------|------|------|
| 纯 CoT（Chain-of-Thought） | 只在脑内推理，不接触外部 | 事实性幻觉无法自纠 |
| 纯 Acting（无推理） | 直接调工具 | 无计划、易跑偏、难恢复 |
| **ReAct** | 推理与行动**交替** | 步数/成本/可控性成为新的工程问题 |

## 1.2 原始形态：一步一步看

以"用户说没收到货"为例，原始的文本 ReAct 长这样：

```
Thought: 我需要先查订单状态
Action: get_order
Action Input: {"order_id": "123"}
Observation: {"status": "shipped", "carrier": "SF"}
Thought: 订单已发货，但用户说没收到，需要查物流
Action: get_tracking
Action Input: {"tracking_no": "SF123"}
Observation: {"status": "delayed", "eta": "+2天"}
Thought: 物流延误，需要查补偿政策
Action: retrieve_kb
Action Input: "延误补偿政策"
Observation: "延误超过24小时补偿10元"
Thought: 可以申请补偿
Action: apply_compensation
Action Input: {"order_id": "123", "amount": 10}
Observation: {"success": true}
Final: 您的订单因物流延误，已为您申请10元补偿。
```

拆解成四类信息：

| 标记 | 含义 | 谁来产生 |
|------|------|---------|
| `Thought` | 内部推理，不进工具 | LLM |
| `Action` / `Action Input` | 想调用的工具与参数 | LLM |
| `Observation` | 工具真实返回，**事实来源** | 工具/环境 |
| `Final` | 终止信号 | LLM |

**关键点**：Observation 是外部世界的**真值**。LLM 不能自己编 Observation —— 这条边界一旦破了（比如让模型"模拟"工具结果），ReAct 就退化回幻觉。

## 1.3 架构视角：它就是一个状态机

ReAct 的架构本质是一个**显式状态机**：

| 要素 | 内容 |
|------|------|
| **状态** | 当前上下文、历史步骤、记忆、工具结果 |
| **转移** | 由 LLM 决定下一步：继续调工具，还是输出最终答案 |
| **动作** | 工具 / API / 代码 / 检索 / 数据库操作 |
| **观察** | 工具返回结果，经**清洗、截断、摘要**后写回上下文 |
| **终止** | Final Answer、最大步数、超时、预算耗尽、人工终止 |

把这几项写成状态图：

```
        ┌──────────────────────────────────────────┐
        │                                          │
   [用户输入]                                     │
        │                                          │
        ▼                                          │
   ┌─────────┐    LLM 决策     ┌──────────────┐   │
   │ Thought │ ─────────────▶ │ 调用工具？    │   │
   └─────────┘                └──────┬───────┘   │
                                     │            │
                    是 ──────────────┤ 否         │
                    │                             │
                    ▼                             │
              ┌──────────┐                        │
              │  Action  │  ← 策略/权限/预算检查   │
              └────┬─────┘                        │
                   ▼                              │
              ┌──────────────┐                    │
              │ Observation  │  清洗·截断·摘要     │
              └──────┬───────┘                    │
                     └──────────▶ 写回上下文 ─────┘
                                     │
                     否 ────────────┘
                     ▼
              ┌──────────────┐
              │ Final Answer │ → Guardrail → 返回
              └──────────────┘

  终止条件（任一命中即退出）：Final / max_steps / 超时 / 预算耗尽 / 人工终止
```

## 1.4 生产级的第一条改造：别用文本解析

**原始 ReAct 用正则去解析 `Action:` 文本，这在生产里非常脆弱**：

- 模型少写一个冒号、多一段解释、换行位置不对 → 解析失败 → 整轮报废
- 无法严格约束参数类型 → `amount: "-100"` 也能传进去

所以生产级一律改用 **Function Calling / JSON Schema / Tool Calls** 做结构化输出：

| | 原始文本 ReAct | 生产级 |
|---|---|---|
| Action 载体 | 自由文本 + 正则解析 | JSON Schema / Tool Call |
| 解析失败率 | 高，需重试 | 低（由模型侧约束） |
| 参数校验 | 事后手工校验 | Schema 强校验 |
| 多工具并行 | 难 | 原生支持 |

> 记住这条关系：**ReAct 是模式，Function Calling 是接口。** 生产系统用结构化工具调用**替代**原始文本 ReAct，但模式本身没变。

## 1.5 为什么 ReAct 有效

论文里的证据（PaLM-540B）：

| 任务类型 | 基准 | ReAct 的作用 |
|---------|------|-------------|
| HotpotQA / FEVER（知识密集问答） | 减少幻觉 | 用检索到的外部事实锚定推理 |
| ALFWorld / WebShop（交互式决策） | 提升任务成功率 | 「推理 + 行动」比纯行动更有计划性 |

一句话：**它把"可能编造"的生成任务，转换成"可以验证"的检索+行动任务。**
