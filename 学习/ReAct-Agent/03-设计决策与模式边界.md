# 03 · 设计决策与模式边界

## 3.1 四种模式怎么选

| 模式 | 本质 | 特点 | 适用场景 |
|------|------|------|---------|
| **ReAct** | 控制模式 | 边想边做，动态调用工具 | 路径不确定、需外部事实、动态决策 |
| **Function Calling** | 接口协议 | 结构化工具调用 | 生产级 Action 输出的**载体** |
| **Plan-and-Execute** | ReAct 的高层变体 | 先计划再执行 | 复杂**可分解**任务 |
| **Workflow** | 确定性编排 | 流程固定、可枚举 | 稳定、合规、高频业务 |

它们**不是互斥的四个选项**，而是不同层次的东西：

```
    ┌─────────────────────────────────────────────┐
    │  Plan-and-Execute  （先拆解任务）            │   ← 决策层
    │    └── ReAct       （边想边做地执行）        │   ← 控制层
    │          └── Function Calling（怎么调工具）  │   ← 接口层
    └─────────────────────────────────────────────┘
              Workflow  （把确定的路径固化下来）      ← 编排层
```

## 3.2 生产常见形态：混合

```
高层 Planner 拆解任务
        │
        ▼
低层 ReAct 执行
        │
        ├── 确定性步骤 ──▶ Workflow
        └── 高风险步骤 ──▶ HITL（人工确认）
```

**核心判断**：拿"路径是否可枚举"当分水岭。

| 问自己 | 是 → | 否 → |
|--------|------|------|
| 步骤能不能提前穷举？ | Workflow | ReAct |
| 任务能不能先拆成子任务？ | Plan-and-Execute | 直接 ReAct |
| 有没有不可逆副作用？ | 加 HITL | 可自动执行 |

## 3.3 反模式：不要为了 Agent 而 Agent

> 客服退换货、审批流这类**场景确定**的业务，Workflow 更稳、更便宜、更可审计。
> 只有**长尾、探索型**问题才值得上 ReAct。

上 Agent 的代价是显式的：

- 延迟变不可预测（步数不定）
- 成本变不可预测（token 随观察膨胀）
- 结果不可复现（同一输入可能走不同路径）
- 需要额外的治理设施（网关、权限、审计、Eval）

如果一个流程能画成流程图，就**别**用 Agent。

## 3.4 架构师必须回答的八个设计问题

| 问题 | 生产做法 |
|------|---------|
| 工具太多选不准 | 工具分组、Router、**Tool RAG** 检索工具 |
| 观察太长 | 截断、字段裁剪、小模型摘要 |
| 模型不按格式输出 | Function Calling、JSON Mode、解析重试 |
| 死循环 | `max_steps`、重复动作检测、状态哈希 |
| 成本/延迟高 | 小模型路由、缓存、并行工具调用 |
| 提示注入 | 工具结果标记为**不可信**、最小权限、输出过滤 |
| 高风险动作 | HITL、审批流、沙箱、回滚 |
| 不可观测 | Trace、Span、每步日志、回放、Eval |

## 3.5 边界上的两个高频判断题

**Q：ReAct 会不会取代 Workflow？**
A：不会。ReAct 适合动态决策，Workflow 适合确定性、强合规。两者互补，生产里通常是混合架构（如阿里百炼、字节 Coze 的"工作流 + 插件 + 知识库 + Agent"）。

**Q：Function Calling 是不是就是 ReAct？**
A：不是。Function Calling 只解决"**怎么把 Action 结构化地表达出来**"，它不包含循环控制、终止判断、治理。没有 Runtime 的 Function Calling 只是单次工具调用。
