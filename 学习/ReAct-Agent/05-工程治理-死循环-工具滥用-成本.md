# 05 · 工程治理：死循环 · 工具滥用 · 成本失控

> 这是 ReAct 生产化**最核心的难点**。面试官问这个，不是想听"加个 max_steps 就行"，而是想看你能不能把 Agent 当成一个有状态、有预算、有权限、有监控的**运行时系统**来治理。

一句话总纲：

> **模型负责思考，Runtime 负责刹车；工具负责执行，网关负责治理；Trace 负责可观测。**

---

# 一、死循环：ReAct 为什么会"鬼打墙"

## 1.1 六类原因

死循环不是模型笨，通常是**系统设计缺了外部刹车**。

| 类型 | 表现 | 例子 |
|------|------|------|
| 重复动作 | 反复调同一工具、同样参数 | 一直 `get_order(123)` |
| 无进展 | 每步结果差不多，模型觉得还没完成 | 反复搜同一个关键词 |
| 工具失败重试 | 工具报错，模型不改策略，反复重试 | 一直 `run_sql` 失败 |
| 格式错误 | 模型输出解析不了，编排层重试 | `Action` 字段缺失 |
| 目标漂移 | 越跑越偏，忘了原始任务 | 本来查物流，跑去查天气 |
| 上下文污染 | 旧观察太长，模型忽略关键信息 | 重复问已经知道的事 |

## 1.2 硬控制：不依赖模型，编排层强制执行

**这是第一道防线，也是最可靠的。不要指望 Prompt 让模型"别循环"，必须由 Runtime 强制。**

### ① 最大步数 max_steps

最简单有效，比如 8~15 步。超过就：

- 强制进入「总结模式」：只允许输出 Final Answer
- 或转人工、返回兜底话术

```python
if step >= max_steps:
    return force_final_answer(history)
```

### ② 动作哈希去重

对 `action + args` 做**规范化哈希**（`sort_keys=True` 保证同一组参数哈希一致），记录出现次数。

```python
key = hash(action + json.dumps(args, sort_keys=True))
count = action_counter[key] + 1
action_counter[key] = count

if count == 2:
    inject_hint("你已执行过相同动作，请换策略或直接回答")
elif count >= 3:
    terminate("重复动作过多")
```

效果示例：

| 第几次 `get_order(123)` | 处理 |
|------------------------|------|
| 第 1 次 | 正常执行 |
| 第 2 次 | 注入提示："你已查过订单，请查物流或直接回答" |
| 第 3 次 | 强制终止，转人工 |

### ③ 状态哈希 / 观察相似度

**动作不同但结果没变化，也算无进展。**

```python
state = extract_key_fields(observation)   # 比如订单状态、物流状态
if similar(state, last_state) > 0.95:
    no_progress_count += 1
else:
    no_progress_count = 0

if no_progress_count >= 2:
    inject_hint("连续两步没有新信息，请重新规划或给出最终答案")
if no_progress_count >= 3:
    terminate("无进展")
```

### ④ 预算耗尽

时间、token、工具调用次数、金额 —— **任一超限即终止**。

```python
if elapsed > 30s:        terminate("超时")
if tokens_used > 8000:   terminate("token预算耗尽")
if tool_calls > 10:      terminate("工具调用超限")
```

### ⑤ 工具失败熔断

同一工具连续失败 2 次，**禁用一段时间**，逼模型换方法。

```python
if tool_fail_count[tool] >= 2:
    disable_tool(tool, duration=60s)
    observation = "该工具暂时不可用，请换其他方法"
```

## 1.3 软控制：通过提示引导模型

硬控制是**刹车**，软控制是**方向盘**。系统提示里可以加：

```
- 如果连续两次得到相同结果，不要重复调用，请换策略或总结。
- 每次行动前，先判断是否已经拥有足够信息。
- 如果工具报错，先分析原因，不要盲目重试。
- 最多尝试 3 种不同方法，之后必须给出最终答案。
```

> ⚠️ **软控制只能减少概率，不能兜底。** 必须叠在硬控制之上。

## 1.4 死循环排查清单（线上按此顺序查）

1. 看 Trace：**哪一步开始重复？**
2. 动作是否相同？参数是否相同？
3. 观察是否被**截断**，导致模型看不到关键信息？
4. 工具是否一直报错？
5. 系统提示是否太长，模型忽略了"不要重复"？
6. 是否**缺少** `max_steps` / 去重逻辑？

# 二、工具滥用：模型为什么乱调工具

## 2.1 表现与原因

**六种表现**：调了不必要的工具、一次调太多、参数乱传、调高风险工具、重复调同一个、用错工具。

**六类原因**：

| 原因 | 说明 |
|------|------|
| 工具描述模糊 | `search` 和 `retrieve_kb` 功能重叠，模型不知道选哪个 |
| 工具太多 | 一次给 50 个工具，容易乱选 |
| 模型"保险心理" | 为了确保正确，同时调多个相似工具 |
| 没有成本意识 | 模型不知道每次调用要花钱 |
| 权限太宽 | 模型能调退款、删除，但没有审批 |
| 参数校验缺失 | 模型传 `amount: -100` 也放行 |

## 2.2 防护：工具网关 + 策略引擎

生产级**不会让模型直接调工具**，而是经过 Tool Gateway：

```
LLM → Tool Gateway → Policy Engine → Rate Limiter → Validator → Executor → Cache → Audit
```

### ① 工具分组 + Tool RAG

不要把所有工具塞给模型。先按领域分组：

| 组 | 工具示例 |
|----|---------|
| 订单组 | `get_order`、`get_tracking`、`apply_refund` |
| 知识组 | `search_kb`、`search_web` |
| 代码组 | `run_code`、`read_file`、`apply_patch` |

然后用 **Router LLM** 或 embedding 检索，**只给当前任务相关的 5~10 个工具**。

### ② 工具描述精确化

差的描述（会让模型选错）：

```json
{"name": "search", "description": "搜索信息"}
```

好的描述（明确边界与反例）：

```json
{
  "name": "search_order",
  "description": "根据订单号查询订单状态。仅当用户提供订单号时使用。不要用于查物流。",
  "parameters": {"order_id": "string, 必填"}
}
```

### ③ 参数校验

用 JSON Schema 严格校验：类型、必填、范围、枚举。

```python
validate_schema(tool_name, args)
if args["amount"] < 0 or args["amount"] > 1000:
    return "金额不合法"
```

### ④ 权限与策略

每个工具执行前检查：**用户有没有权限？当前环境允许吗？是否需要二次确认？**

```python
if tool in HIGH_RISK and not user_confirmed:
    return "需要人工确认"
if not rbac.allow(user, tool, args):
    return "无权限"
```

高风险工具清单：**退款、转账、删除、发邮件、回滚、执行 SQL**。

### ⑤ 速率限制与配额

- 每个用户每分钟最多调 10 次
- 每个任务最多调 10 次工具
- 同一工具连续失败 2 次熔断
- 搜索 API 按次收费，单独配额

### ⑥ 幂等与去重（写操作必做）

```python
idempotency_key = f"{user_id}:{task_id}:{tool_name}:{args_hash}"
if redis.exists(idempotency_key):
    return cached_result
```

### ⑦ 工具成本标签

在工具 schema 里加成本提示，**让模型自己有成本意识**：

```json
{
  "name": "search_web",
  "description": "搜索网页，每次调用成本较高，仅在知识库无结果时使用。"
}
```

## 2.3 工具滥用排查指标

| 指标 | 含义 |
|------|------|
| 工具选择准确率 | 模型选对工具的比例 |
| 无效调用率 | 调了但没用的比例 |
| 重复调用率 | 同一工具同参数的重复次数占比 |
| 高风险工具调用次数 | 退款/删除类调用量 |
| 人工确认率 | 触发 HITL 的比例 |

# 三、成本失控：钱到底花在哪

## 3.1 四个成本来源

| 来源 | 说明 |
|------|------|
| **LLM token** | 每步都要把历史、工具 schema、观察结果发给模型 |
| **工具调用费** | 搜索 API、数据库、代码执行、第三方服务 |
| **重试与并行** | 失败重试、多 Agent 并行，成本翻倍 |
| **长上下文** | 观察结果太长，token 爆炸 |

## 3.2 八种控制手段

### ① 预算控制

每个任务设**硬预算**：

```python
budget = {
    "max_tokens": 8000,
    "max_tool_calls": 10,
    "max_time": 30,
    "max_cost": 0.5,   # 美元
}
```

### ② 模型路由

**不是每步都用 GPT-4 级别模型。**

| 步骤 | 模型 |
|------|------|
| 简单意图识别、路由 | 小模型 |
| 复杂推理、规划 | 大模型 |
| 工具参数生成 | 中等模型 |
| 最终总结 | 小模型或模板 |

```python
if step == 0 and is_simple_intent(user_input):
    model = "small"
else:
    model = "large"
```

### ③ 上下文压缩 —— **最大的降本点**

| 手段 | 做法 |
|------|------|
| 观察裁剪 | 工具只返回必要字段，不要返回整个 HTML/日志 |
| 摘要 | 旧步骤用小模型摘要成 1~2 句话 |
| 滑动窗口 | 只保留最近 N 步详细内容 |
| 外部化 | 原始结果存 DB/Redis，上下文只放引用 ID |
| schema 精简 | 只给相关工具，描述不要啰嗦 |

```python
# ✅ 只回必要字段
observation = {"status": "shipped", "carrier": "SF", "tracking_no": "SF123"}
# ❌ 而不是整个订单 JSON 几百个字段
```

### ④ 缓存

相同工具调用结果、相同用户问题、相同知识检索，都可缓存。

```python
cache_key = f"{tool}:{args_hash}"
if cache.get(cache_key):
    return cache.get(cache_key)
```

### ⑤ 超时与熔断

工具 3s 超时；LLM 调用 10s 超时；失败重试最多 2 次；连续失败熔断降级到兜底。

### ⑥ 提前终止

如果已经能回答，不要继续调工具 —— 加一个"**信息充足度**"判断：

```python
if enough_info(history):
    return final_answer(history)
```

### ⑦ 并行与批处理

独立工具可并行，但**注意成本**。不要为了并行而并行。

### ⑧ 多 Agent 成本

多 Agent 通信成本高。**能用单 Agent + 工具解决，就别上多 Agent。**

## 3.3 成本监控指标

| 指标 | 说明 |
|------|------|
| token / 任务 | 平均、P99 |
| 成本 / 任务 | 美元 |
| 工具调用次数 / 任务 | 平均、P99 |
| 缓存命中率 | **越高越好** |
| 重复动作率 | **越低越好** |
| 无进展终止率 | **越低越好** |
| 人工接管率 | **越高成本越高** |
| 模型路由比例 | 小模型占比 |

## 3.4 "线上突然变贵"排查顺序

按这个顺序查，通常前两项就能命中：

1. 是否**死循环**导致步数暴涨？
2. 是否**观察结果变长**导致 token 暴涨？
3. 是否缓存失效？
4. 是否小模型路由失效，全走大模型？
5. 是否工具调用次数暴增？
6. 是否多 Agent 对话轮次失控？

# 四、综合：带护栏的 ReAct Runtime

把上面所有护栏串起来的完整骨架（可直接运行的版本见 [09-ReActRuntime参考实现.py](./09-ReActRuntime参考实现.py)）：

```python
class ReActRuntime:
    def __init__(self, user, task):
        self.user, self.task = user, task
        # 预算
        self.max_steps, self.max_tokens = 8, 8000
        self.max_tool_calls, self.max_time = 10, 30
        # 状态
        self.start_time, self.tokens_used, self.tool_calls = now(), 0, 0
        self.action_history, self.state_history, self.no_progress = [], [], 0

    def run(self):
        history = build_initial_prompt(self.user, self.task)

        for step in range(self.max_steps):
            # 1. 预算检查
            if now() - self.start_time > self.max_time:
                return fallback("超时")
            if self.tokens_used > self.max_tokens:
                return fallback("token预算耗尽")
            if self.tool_calls > self.max_tool_calls:
                return fallback("工具调用超限")

            # 2. 模型决策
            out = llm(history, tools=select_tools(self.task))
            self.tokens_used += out.usage
            if out.type == "final":
                return guardrail(out.content)

            # 3. 动作去重
            action_key = hash(out.action + json.dumps(out.args, sort_keys=True))
            count = self.action_history.count(action_key)
            if count >= 2:
                history.append(hint("你已重复该动作，请换策略或直接回答"))
                continue
            if count >= 3:
                return fallback("重复动作过多")
            self.action_history.append(action_key)

            # 4. 策略检查 + 5. 工具执行（带缓存/超时/限流）
            if not policy.allow(self.user, out.action, out.args):
                observation = "拒绝：无权限或需人工确认"
            else:
                observation = tool_gateway.execute(
                    self.user, out.action, out.args,
                    timeout=3, cache=True, rate_limit=True,
                )
                self.tool_calls += 1

            # 6. 观察压缩
            observation = summarize_and_truncate(observation)

            # 7. 无进展检测
            state = extract_state(observation)
            prev = self.state_history[-1] if self.state_history else None
            self.no_progress = self.no_progress + 1 if similar(state, prev) > 0.95 else 0
            self.state_history.append(state)

            if self.no_progress >= 2:
                history.append(hint("连续无新信息，请重新规划或给出最终答案"))
            if self.no_progress >= 3:
                return fallback("无进展")

            history.append({
                "thought": out.thought,
                "action": out.action,
                "observation": observation,
            })

        return fallback("达到最大步数")
```

> **这个 Runtime 里，模型只负责决策，刹车全在编排层。**

> ⚠️ 上面伪代码有 **3 处需要落地时修正的缺陷**，已在 [09-ReActRuntime参考实现.py](./09-ReActRuntime参考实现.py) 中修好并实跑验证：
> ① 动作去重的 `count >= 2 → continue` 会跳过计数 append，导致计数永远停在 2 → **无限注入提示**；
> ② 熔断判断应放在工具执行**之前**，否则已熔断的工具仍会被调用一次；
> ③ 无进展提示应只注入一次（`== 2` 而非 `>= 2`），提示本身也是 token 成本。

## 大厂对应实践

| 问题 | 大厂做法 |
|------|---------|
| 死循环 | OpenAI Agents SDK 有 `max_turns`；Bedrock Agents 有 orchestration 限制；Copilot 有重试次数 |
| 工具滥用 | OpenAI Function Calling 严格 schema；AWS Action Group + IAM；国内平台插件分组 |
| 成本失控 | 模型路由、缓存、上下文压缩、预算控制；字节/阿里内部平台都有配额和计费 |
| 高风险 | Copilot diff 确认；银行 Agent 二次确认；AWS IAM + HITL |
