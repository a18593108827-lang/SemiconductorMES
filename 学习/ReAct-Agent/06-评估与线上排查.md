# 06 · 评估与线上排查

> 没有 Trace 和 Eval，Agent 就只能靠"感觉"迭代。这一节讲怎么把"感觉"换成"证据"。

## 6.1 评估指标

| 类别 | 指标 |
|------|------|
| **结果质量** | 最终答案准确率 |
| **过程质量** | 工具选择准确率、参数准确率 |
| **效率** | 任务成功率、平均步数 |
| **成本** | 成本、延迟、P99 |
| **风险** | 安全违规率、人工接管率 |

> 注意：**只看最终答案准确率是不够的**。一个"答对了但绕了 20 步、多花了 5 倍钱、还调了一次退款接口"的 Agent，在生产上是失败的。过程指标和结果指标要一起看。

## 6.2 评估方法

| 方法 | 说明 |
|------|------|
| **离线 eval set + 轨迹回放** | 固定输入集，回放每次的 Thought/Action/Observation，比对新旧版本 |
| **在线 A/B** | 灰度分流对比成功率与成本 |
| **人工评分** | 对抽样轨迹打分，尤其针对高风险动作 |
| **失败案例归因** | 每个失败样本归类到"选错工具/参数错/循环/权限拒绝/上下文丢失"等，量化分布 |

**轨迹回放是关键**：Agent 的评测对象不只是"最终答案"，而是**整条轨迹**。同一个答案，路径差异可能意味着稳定性、成本、风险的巨大差异。

## 6.3 线上排查：看 Trace 时问什么

```
哪一步工具慢？
Observation 是否过长？
模型是否重复动作？
工具是否报错 / 权限拒绝？
上下文是否溢出？
是否命中缓存 / 降级？
```

## 6.4 失败回放必须记录的元素

> 每次失败都要能**完整回放**。缺一样，这次失败就白费了。

| # | 元素 |
|---|------|
| 1 | 用户输入（原始，未加工） |
| 2 | 系统提示（当轮实际生效版本） |
| 3 | 每一步的 `Thought` |
| 4 | 每一步的 `Action`（含参数） |
| 5 | 每一步的 `Observation`（原始 + 压缩后） |
| 6 | token 用量 |
| 7 | 延迟 |
| 8 | 成本 |

**为什么要记"原始 + 压缩后"两份 Observation？** 因为很多"模型看不到关键信息"的 bug，根因在压缩环节 —— 只留压缩后的版本，就永远查不出来。

## 6.5 一个实用原则：可复现优先于可调优

面对线上问题，先问"**能不能复现**"：

| 能复现 | 不能复现 |
|--------|---------|
| 用回放数据锁定某一步，直接改逻辑或 Prompt，写回归用例 | 只能加强 Trace 与防护（预算、熔断、HITL），先止血 |

## 6.6 常见追问：线上突然变贵怎么办？

按 [05 · 成本章节](./05-工程治理-死循环-工具滥用-成本.md#34-线上突然变贵排查顺序) 的顺序查：

1. 是否死循环导致步数暴涨？
2. 是否观察结果变长导致 token 暴涨？
3. 是否缓存失效？
4. 是否小模型路由失效？
5. 是否工具调用次数暴增？
6. 是否多 Agent 对话轮次失控？
