# 07 · 多 Agent 协作

## 7.1 三种常见模式

| 模式 | 机制 | 适用 |
|------|------|------|
| **Supervisor + Worker** | 主管 Agent 分派任务，Worker ReAct 执行 | 任务可明确切分 |
| **消息总线** | Agent 间通过消息/共享状态协作 | 需要松耦合、可插拔 |
| **角色隔离** | 检索 Agent、代码 Agent、审查 Agent 权限不同 | 需要权限与职责分离 |

## 7.2 必须配的三个护栏

多 Agent 直接把单 Agent 的死循环问题**放大数倍** —— 因为会互相等待、互相触发。

| 护栏 | 说明 |
|------|------|
| **最大轮次** | 全局轮次上限，不是每个 Agent 各自算 |
| **终止条件** | 显式定义"完成"和"失败"的信号 |
| **仲裁者** | 出现分歧时由仲裁 Agent（或规则）强制推进 |

## 7.3 大厂实践

| 平台 | 做法 |
|------|------|
| Microsoft AutoGen | 多 Agent 对话（`AssistantAgent` 提议、`UserProxyAgent` 执行） |
| MetaGPT | 角色分工（产品经理/架构师/工程师…） |
| GitHub Copilot | Planner / Coder / Reviewer 分工 |

## 7.4 反模式：多 Agent 不是越多越好

> **通信成本和一致性是大问题。能用单 Agent + 工具解决，就别上多 Agent。**

多 Agent 的隐藏代价：

| 代价 | 说明 |
|------|------|
| 通信成本 | 每条消息都是一次 LLM 调用 |
| 一致性 | 多个 Agent 对同一状态的理解可能不一致 |
| 调试难度 | 失败要跨 Agent 关联 Trace |
| 死锁 | 互相等待，谁都不推进 |
| 轮次爆炸 | N 个 Agent 两两对话，轮次增长快 |

**判断标准**：如果任务能拆成"串行流水线"，用 Workflow 就够；只有需要"多视角博弈/互相审查"时才上多 Agent。

## 7.5 常见追问：多 Agent 死锁怎么办？

答：**超时 + 轮次限制 + 仲裁 Agent + 状态机强制推进**，四件套一起上。核心思路和单 Agent 的护栏一致 —— **不依赖 Agent 自觉，靠 Runtime 强制**。
